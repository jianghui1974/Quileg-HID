## 0. 开工 30 秒检查

```text
status()      → device / screen / calibrated
screenshot()  → 当前页、列、键盘状态、是否有弹窗
```

- `screen=false`：等 2 s 再看一次；仍 false 就请人重开「屏幕镜像」，不要反复重试。
- `calibrated=false`：不要盲点，先跑校准。
- **截图可能晚一帧**：每个动作后多截一张再判断，否则会把「已提交」看成「还在输入」。
- 主屏有**多页、每页列数不同**：同一坐标在不同页可能是不同 App，先看截图再点。

> **iPhone 端三个总开关（每次新设备/换机必查，埋得很深）**
>
> 1. **辅助触控必须开**：`设置 → 辅助功能 → 触控 → 辅助触控`。不开就没有鼠标指针，
>    所有 click/move 都像“没反应”。
> 2. **鼠标键「使用主键盘」必须关**：`设置 → 辅助功能 → 触控 → 辅助触控 → 指针设备 →
>    鼠标键 → 使用主键盘`。开着时键盘被当成鼠标：`i j k l m o u 7 8 9 .` 不落屏、
>    回车不换行而是弹菜单、指针乱跳。**这是 2026-10-22「11 个字符永不落屏」的真正原因**，
>    关掉立即恢复，不需要重启手机。
> 3. **自动锁定必须设「永不」**：`设置 → 显示与亮度 → 自动锁定`（iPhone / iPad 同）。
>    锁屏会让投屏停住 —— 日常操作表现为「截图不动」，校准跑到一半锁屏就是整轮作废
>    （`canvas` 类中断）。这是唯一一个「不设也能开始、跑到一半才炸」的开关，装完就该提醒用户。

> **反模式：别自己发明流程（会浪费大量时间，而且不可靠）**
>
> - ❌ 手改 `calib.json` / 自己补像素偏移 / “这次先 +0.02 试试”——校准错了就 `calibration_request`；
> - ❌ 不用 `click_text` 而靠目测坐标反复盲点；不用 `scroll(fine)` 而自己拼拖拽；
> - ❌ 连续 `changed=false` 不换目标、不查日志，闭眼重试；
> - ❌ 绕过 MCP 直接 `curl /api/raw` 或写脚本操作手机（排障例外，要说明）；
> - ❌ 自己跑校准向导（必须用户点「开始」）；
> - ❌ 遇到问题先怀疑固件/重装 App，而不是先看 `status` / `app_logs`。
>
> **先翻 AI_GUIDE §1.0 的工具表，再动手。摸索 10 分钟不如查表 10 秒。**

### 0.1 新设备 / 新场景：先建立基线

用户可能换 iPhone / iPad、换 iOS 版本、换指针大小、换网络。**同一套坐标、滚动距离、返回手势不要跨设备复用。**

第一次接触一台设备或一个 App，先记下：

| 项 | 怎么取 |
|---|---|
| 设备 / 系统 | 用户告知，或从屏幕「关于本机」看 |
| 指针大小 | 设置 → 辅助功能 → 触控 → 辅助触控 → 指针控制 |
| 镜像分辨率 | `status()` 的 `aspect`、截图尺寸 |
| 校准 | `calibrated` + `control/calib.json` 里对应的 `profiles` 键 |
| 投屏延迟 | 校准向导第一步会测（这台 0.53 s） |
| BLE | `status` 里 `connected/encrypted/sub/kb/ms` |

然后用计算器 `7+8=15` 验证这张表是否适合当前设备。**不要凭“上次也是 iPhone”就直接操作。**

基线写进 §6.1，任务中的新发现写进对应小节；下一个 AI 先翻这里，再动手。

## 1. 屏幕源（AirPlay）

| 现象 | 根因 | 规避 |
|---|---|---|
| App 打开后画面变横屏、随后**冻结**，点击/滚动帧 hash 不变 | 部分第三方 App 的投屏保护（实测） | 换 App；或用 UVC 采集绕过；不要重校准（不是坐标问题） |
| 使用上述 App 期间 `screen=false` 两次，其中一次 UxPlay 被看门狗重启 | 投屏会话被 App 带崩 | 等 / 请人重投屏；不要连续操作 |
| 同局域网多台 Mac 的投屏名都叫 `Quileg` | 接收端名写死 | 现为 `Quileg - <电脑名> (4位ID)`，每台唯一；BLE 名本身带 MAC 后缀 |
| 画面静止时取不到新帧 | AirPlay 只在画面变化时发帧 | 用「画面变化」判断，不要用「帧新鲜度」 |
| 长距离移动时 409 | BLE + Wi-Fi 共存抖动 | 409 后 `ensure_ble()` + 重试；画图/校准都要包重试 |
| 横屏 App 下点击系统性偏移 | 校准表是竖屏的，宽高比从 0.463 变 1.778 | 不要硬点；换竖屏页或重新校准 |
| 所有工具突然 `connection refused` | App 被 ⌘Q 退出（0.5.0 起关窗只是隐藏） | 让用户看 Dock / 重开 App；不要重投屏 |

## 2. 输入（中文 / 英文 / 标点）

- **九宫格不可用**：硬件键盘连接时 iOS 隐藏软键盘，九宫格点不到；即使能显示，每键 4–7 s。**用全键盘**。
- **候选选择用数字键** `1`–`9`；**空格只移动高亮，不提交**。
- **候选顺序不固定**：`荀彧` 是第 3 个、`使` 是第 4 个、`至` 是第 4 个。按数字前先看候选内容。
- **英文候选是标签符号**：拼音模式下打 `abc`，选 `ABC/abc` 插入的是灰色胶囊（退格整块删除），不是普通文本。要普通英文先 `ctrl+space` 切英文输入法。
- **标点宽度不统一**：输入 `123,456.789!` 实际得到 `123,456.789！`（逗号/句点半角、感叹号全角）。不要假设 1:1。
- **整句拼音可行**：`woxihuanbeijing` → 「我喜欢北京」；`nihao` → 「你好」。名句命中率高，冷门内容要分段。
- **生僻字用组词法**：`xunyu`→荀彧→`←`退格→`⌘→`；`caojianrenming`→草菅人命→删字→`⌘→`。
- **删字后必须回行尾**：退格只删字符不移动光标；不 `⌘→` 就继续输入会插到目标字前面（实测 `9菅` vs `菅8`）。
- **软键盘不显示 ≠ 没聚焦**：看蓝色边框/光标，或用 `Tab` 切焦点。
- **`type_text` 仅接受 ASCII**：中文通道已移除；中文改用拼音 + 截图/OCR 判断候选 + `click_text` 点选，不依赖任何外部服务器。
- **切 App：iPhone 上没有 `cmd+tab`**（2026-10-22 实测 `cmd+tab` / `shift+cmd+tab` 都无反应，iPadOS 未验证）。
  用 `cmd+h` 回主屏 → `cmd+space` 搜名字打开；`cmd+h` 本轮 2/2 生效。App 内标签可试 `cmd+1`–`cmd+9`。
- **`Tab` 会被中文输入法吃掉**：弹出候选栏，不是焦点导航；先 `ctrl+space` 切英文。
- **`Enter` 常只提交候选词**，不激活界面元素；Spotlight/备忘录里失败时改用 `click_text`。
- **`type_text` 含非 ASCII 会直接报错**：这是预期行为；先改写拼音，再用 OCR 点候选。

### 2.1 部分字符不落屏 / 回车弹菜单：鼠标键「使用主键盘」被打开（2026-10-23 更正）

**现象**：`type_text`、App 软键盘、`POST /api/raw {"text":"type i"}` 三条路都一样——在备忘录/Spotlight 里
下面 11 个字符**从不落屏**，其余字母数字、大小写、标点、顺序全部正常：

```text
i j k l m o u 7 8 9 .
usage: 0x0C 0x0D 0x0E 0x0F 0x10 | 0x12 | 0x18 | 0x24 0x25 0x26 | 0x37
```

同时还有两个伴随症状：**回车不换行，而是弹出功能选项/菜单**；指针有时自己乱跳。

**根因（2026-10-23 用户定位）**：iPhone 的
`设置 → 辅助功能 → 触控 → 辅助触控 → 指针设备 → 鼠标键 → 使用主键盘` **被打开了**。
键盘被系统当成鼠标：`i/j/k/l` 移动、`u/o` 点击、`7/8/9` 方向、`.` 等，Return 被当作点击。
这 11 个正好是鼠标键的键位——**不是固件坏，也不是 HID 键位状态坏**。

**恢复**：把 **使用主键盘** 关掉（不需要时把 **鼠标键** 也关掉），**立即恢复**；
不需要重启 iPhone、不需要重配对。

**前置**：`辅助触控` 必须开着，否则 iPhone 上根本没有鼠标指针（见 §0）。

**为什么之前误判**：2026-10-22 那次靠「重启 iPhone」恢复了，于是归因为“HID 键位状态坏了”；
实际是设置开关的问题（重启/重配后开关被重置或后续被关掉）。**现在以开关状态为准。**

**同一块板 + 同一固件，只换宿主**（当时的证据，结论仍成立——手机侧设置问题）：

| 宿主 | 结果 |
|---|---|
| macOS（Sublime Text） | ✅ `aib ijklm 789.` 14 个字符全落屏 |
| iPadOS 18（备忘录） | ✅ `hijklm` 全部进入拼音组合 |
| 这台 iPhone（iOS 18） | ❌ 11 个全丢（当时鼠标键开着） |

**已排除**（别重复走这几步）：

| 假设 | 实测结果 |
|---|---|
| 固件 `kLayout` 写错 / 出厂镜像旧 | 源码表与 `app-16m.bin`、`factory-16m.bin` 逐字节一致；`key i` 返回 `ok`（不是 `err unknown key`），说明运行时映射非零 |
| 按压时长太短、被 iOS 合并 | `type`（10 ms）与 `key`（40 ms）同样丢 |
| 大小写 / Shift / ⌘ 组合 | 小写、大写、`⌘I` 全丢；同一修饰键下 `⌘B`（0x05）正常 |
| 报告槽位（第 1 槽被特殊处理） | `key h+i`（同一报告 `keys[0]=0x0B, keys[1]=0x0C`）只出 `h`，`i` 在槽 2 也丢 |
| 中文输入法 / 硬件键盘布局 | 删除中文输入法、确认「英语（美国）/ ANSI」后现象不变 |
| 文本替换（自定义短语） | 列表只有 1 条正常替换，无空映射 |
| 绑定 / 描述符缓存 | 忽略设备重配后现象不变（当时重启才“恢复”，实为开关状态变化） |

**排查顺序（以后照这个走，别先怀疑固件）**：

1. `type_text("aib")` 自检，确认是「部分字符」还是「完全打不进去」；
2. **换宿主**（Mac 或 iPad）打同一串：换了就好 = 手机侧问题，**不要动固件、不要重校准**；
3. **先查手机两个开关**：辅助触控 = 开；指针设备 → 鼠标键 → 使用主键盘 = 关；
4. 仍不行再：重启 iPhone → 重新配对 → 还原键盘词典 → 第二台 iPhone 对照。

### 2.2 语音桥：Mac 朗读 → 手机听写（2026-10-23 实测）

**用途**：中文输入最慢的是点候选；让 Mac 用 `speak()` 朗读、手机输入法听写，直接上屏。
`speak` → `/api/speech` → 系统 `say`。

**起停方式**：**双击 Control 开始，单击 Control 停止**（不需要点屏幕麦克风）。
MCP 调用：`dictation("start")` / `dictation("stop")`（0.6.0 起）。
它会先按一次 Shift 唤醒 HID 键盘，再双击/单击 Control —— **iOS 会吞掉空闲后的第一次按键**，
直接 `key(combo="ctrl", repeat=2, gap_ms=60)` 常常只算一次 Control，听写起不来（2026-10-23 实测）。

- 前提：手机 `设置 → 通用 → 键盘 → 听写 → 听写快捷键 = Control`（选项只有 **Control / Command / 无**）；
- 实测**两次按下间隔 60 ms 有效**；150 / 350 / 500 ms 都没反应，固定用 60 ms；
- 光标必须在文本框里；**软键盘开或关都行**（关了也能起）；
- 正在听的样子：状态栏**橙点** + 光标旁**黄色小麦克风** + 键盘右下角麦克风变深色停止键；
  黄色小麦克风很小、容易被忽略——它是“正在听”的唯一提示。

**三个坑**

| 现象 | 根因 | 规避 |
|---|---|---|
| 只落前几个字，后面没有 | **转写延迟 1.5–3 s**，截图/OCR 太早 | 说完等 2–3 s 再验收；同一句多截一帧，第二帧才完整 |
| 小麦克风变“暂停态”后再说话没反应 | 误以为暂停 = 停止 | 暂停态**照常收音**，直接说下一句即可；真停了会连橙点一起消失 |
| Spotlight 搜索框说完什么都不进 | 搜索框不走同一条转写路径（实测 2/2 空白） | 用备忘录 / 短信等真实文本框验收 |

**其他实测**：`F5`（Apple 键盘听写键）无效且会收起软键盘；Mac 音量 56% 够用；
自动标点（`，` `。`）和自动换行由 iOS 加，不是 `speak` 加的；单会话约 **30 s 无话音**自动结束。

**与拼音点选的关系**：语音桥快，但依赖扬声器/麦克风/环境噪声；关键内容仍要 OCR 复核，
听写不可用时回退 §2 的拼音 + 候选点选。

> 证据：操作员 2026-10-23 实测（iPhone iOS 18 / 固件 0.7.0 / App 0.9.25）：
> 听写快捷键设置、两句连续落屏、单击 Control 停止的截图。

### 2.3 Intel 版 OCR：`.accurate` 不可用时自动降级 `.fast`（2026-10-24 实测）

**现象**：Intel 包（x86_64）调 `ocr` / `click_text` 时，Vision 的 `.accurate` 识别直接报错
`TextRecognition.CRImageReaderError 9`，`ocr-text` 返回 `vision request failed`，OCR 全不可用。

**实测（同一张图，同一个 `ocr.swift`）**：

| 请求 | arm64 | x86_64（Rosetta / Intel 代码路径） |
|---|---|---|
| `VNDetectRectanglesRequest` | OK | OK |
| `VNDetectBarcodesRequest` | OK | OK |
| `VNRecognizeTextRequest` `.fast`（rev 1/2/3） | OK | **OK** |
| `VNRecognizeTextRequest` `.accurate`（rev 1/2/3） | OK | **全部 CRImageReaderError 9** |

也就是说不是 Vision 整体坏掉，而是 **`.accurate` 用的那套 TextRecognition 模型在 x86_64 上跑不了**
（macOS 26 时代的模型只带 ARM 内核的可能性很大；真 Intel 机器上很可能一样）。

**处理**：`control/ocr.swift` 先试 `.accurate`，失败后自动用 `.fast` 重试，并在 stderr 打一行
`ocr: accurate 不可用，已降级为 fast`。**功能不中断，准确率略降**（短标签/数字仍可用，
长文与生僻字更容易错；要点选候选时先用 `ocr()` 看清结果再点）。

**判断自己是不是这种情况**：`app_logs(grep="ocr")` 或直接跑
`"Quileg HID.app/Contents/Frameworks/control/bin/ocr-text" <图>` 看有没有那行降级提示。
arm64 机器上不会出现。

**没做**：给 Intel 换第三方 OCR 引擎（体积、许可、中文质量都要重评）。
真机上如果 `.fast` 也不够用，再考虑。

### 2.4 iPad「锁屏」其实是顶边面板（2026-10-24 真机定案）

**现象**：被控设备是 iPad（iPadOS 26）时，指针移到左上角/顶边，屏幕变成「锁屏」的样子，
校准与点击全部中断。

**结论（真机实测）**：**不是锁屏，是 iPadOS 26 的顶边手势**——指针碰到屏幕顶边（y≈0）时，
左半区拉下**通知中心**、右半区拉下**控制中心**；两者都是全屏毛玻璃 + 大时钟，看起来和锁屏一样。
`Esc` 能关闭通知中心，点空白能关闭控制中心（两者都实测过）。

**证据（2026-10-24，iPad + 0.7.0 + 0.9.32）**：

| 动作 | 结果 |
|---|---|
| `release 7` → `move -2000 -2000`（纯移动，无点击） | 出现通知中心（x≈0.22） |
| `move 4000 -2000`（到顶边右半） | 出现控制中心 |
| `move -2000 0` / `move 2000 0`（左/右边，y≈0.45） | 正常，无面板 |
| `move 2000 2000`（右下角） | 正常，无面板 |
| 40 小步慢速走到顶边 | 仍出现控制中心（所以是**位置**触发，不是速度） |
| `key esc` | 面板关闭（通知中心/控制中心都试过） |

**为什么每次都会踩到**：`Device.goto_corner()` 的 `home`（40 × `move -127,-127`）必然把指针顶到
(0,0)，所以**每一次移动/点击的归位都会碰顶边**。iPadOS 26 的正常鼠标用户也会遇到同样的事，
不是固件、不是按键、不是校准。

**已排除**：左键卡住（`release 7` 后仍复现）、点击（全程无 `press`/`click`）、
触发角 Hot Corners（四个角都是「无」）、停留控制 Dwell（已关）、自动锁定（设为「永不」，
且 60 秒空闲对照没有锁）。

**规避（0.9.33 起已内置）**：

1. **看错时先按 `Esc`**：能关掉就是面板，不是锁屏（通知中心/控制中心都能关）；
2. **归位改成「底部锚定」**：底边 + 左右边（实测安全）夹住指针，顶角从底边上行
   固定单位到达，**完全不走 `home`**，所以不会再碰 y=0。校准档案里多了三个字段：
   `park: "bottom"`、`park_up: {TL, TR}`（顶角上行单位）、`park_lift`（底角上抬，避开程序坞）；
3. **旧档案仍走旧路径**（`home`），所以 iPhone 等设备不用动；**iPad 要重新校准一次**才会切到新模式；
4. 校准期间别碰设备；自动锁定设「永不」。

**实测（iPad 1554×1080，2026-10-24）**：停车点 TL(0.019,0.056) / TR(0.979,0.056) /
BL(0.027,0.880) / BR(0.977,0.867)，`park_up` 1130/1116，16 个随机点中位误差 25.9 px、
最大 76.6 px，全程无面板。


**教训**：iPad 上的「锁屏」先按 `Esc` 试一下——能关掉的就不是锁屏，是系统面板。

**底部程序坞（2026-10-24 实操发现）**：底部锚定会碰屏幕底边，iPad 的程序坞随即弹出，
盖住最下面约 18%。此时点击「计算器 =」「键盘底行」会命中程序坞，而不是 App。
规避（0.9.34 起内置）：目标 y>0.75 时，先移到画面中部让程序坞收起（等 0.9 s），再下到目标；
比停车点更靠下的目标（底部 ~13%）钳到停车点高度——那一段本来也没有分段表。
实测修复后 `7+8=15`、`9×9=81` 均通过；AirPlay 截图会晚 0.3–0.5 s，验收等 2 s 再截。

**窗口化 vs 全屏幕 App（2026-10-24 用户实测）**：iPadOS 26 的「窗口化 App」模式里，
指针移到窗口边缘会变成缩放/移动光标，顶部还会出现菜单栏，行为更难预测；
**切到「全屏幕 App」后指针形状稳定**。建议校准与日常使用保持同一种显示模式
（`设置 → 多任务与手势 → 全屏幕 App`）。全屏幕模式下实测点击误差 28–36 px，与校准表一致。

### 2.5 底部锚定的钳位只判了一个方向（0.9.34 回归，2026-10-24）

**现象**：iPad 上点屏幕上半部分，指针落在画面顶端（y≈3%），点击完全无效；
没有报错，`calibrated=true`，`changed` 也可能是 true（指针动了）。

**根因**：0.9.34 的程序坞修复给 `move_to` 加了钳位，只判一个方向：

```python
if ref_y is not None and y > ref_y:
    y_eff = ref_y     # 只考虑"比停车点更靠下"
```

底部锚定档案里 TL/TR 的停车点在**顶边**（`ref_y ≈ 0.05`），于是任何 `y > 0.05`
的目标都被钳到 0.05，纵向命令根本不发（抓命令可见只有横向 `move 772 0`）。

**为什么验收没发现**：计算器按键多数走 BR（`nearest_corner` 取距离最小），
钳位条件 `y > 0.86` 不成立，所以 `7+8=15` 照常通过。**验收要覆盖四个象限**。

**修法**：两侧都判——底边停车点钳"更靠下"，顶边停车点钳"更靠上"（0.9.35）。
真值验证：同一张表，目标 `0.5,0.3` 从 210 pt 降到 17 pt。

**判定方法**：在 iPad 上点一个上半屏目标，如果落点贴顶边且 `changed=true`，先查
`move_to` 发出的纵向命令是不是空的。

### 2.6 误选「仅升级」后 Wi-Fi 配不上（分区表不匹配，2026-10-25 实测）

**现象**：板子残留别的分区布局（例如以前刷过别的项目），在固件页选「仅升级固件」→
刷写成功、固件也能启动，但到初始化阶段**Wi-Fi/服务器配置写不进去**。

**根因**：「仅升级」只写 `app0`（0x10000），**分区表原样保留**。如果板子上的
`nvs` 不在 0x9000 / 大小不是 0x5000（本固件的布局），NVS 就落在固件以为之外的区域，
配置写入必然失败——不是「板子没初始化」，而是**分区表不是这一套**。

本固件的分区表（`factory-16m.bin` 内嵌，0x8000 起）：

```
nvs      0x9000  0x5000
otadata  0xe000  0x2000
app0     0x10000 0x140000
app1     0x150000 0x140000
spiffs   0x290000 0x160000
coredump 0x3f0000 0x10000
```

**修法（0.9.38 起）**：刷写前读 0x8000 的 4 KB 分区表并解析（`parse_partition_table` /
`layout_matches`）。只要 nvs 或 app0 对不上，**只允许整包刷写**，并在界面上说明原因：

> 分区表不符（nvs 在 0x1f000/0x6000，本固件要求 0x9000/0x5000）：只能整包刷写

检查只在「检查板子」时做一次（多读 4 KB，约 1–2 秒）。

### 2.7 8 MB 板：「仅升级」报成功但 Wi-Fi 配不上（2026-10-25 已加防呆）

**现象**：8 MB 的板子（例如只焊了 8 MB flash 的 S3）用「仅升级固件」刷 16 MB 布局的包，
esptool 报写入成功、校验通过，固件也起得来，但**配网永远失败**——和 §2.6 同一类结局，
只是根因在 flash 容量而不是分区表内容。整包则会在 `erase_all` **之前**被 esptool 按尺寸拒绝。

**根因**：App 刷写时一直用 `--flash-size keep`，manifest 的 `flash_size: "16MB"` **只用于
界面展示**，从没读过板子的真实容量。8 MB 上 app 只有 1.17 MB，尺寸校验当然过得去。

**修法（2026-10-25，未发版）**：`FirmwareFlasher._write()` 先跑一次
`esptool flash-id`，解析 `Detected flash size: 16MB`，与 manifest 比对：

- 不符 → **在 write-flash 之前**终止（不擦不写、flash 原样保留），UI 显示「已拒绝刷写」；
- 读不到（老芯片 / secure download mode）→ **不拦**，仍由 §2.6 的分区表检查把关。

单测用 `mock.patch` 替掉 `_run_esptool`，断言拒绝发生在 `write-flash` 之前
（`app/tests/test_firmware.py::FlashSizeGuardTest`）。

### 2.8 竖屏 iPhone：探针 HUD 被裁掉 → 校准静默退回帧差（2026-10-25 定位并修复）

**现象**：iPhone（500×1080）自动校准跑到第 55 个点（BR y=30）报
「测不到指针（画面在动/指针不可见）」，13 分钟作废；但同一次校准前面 54 个点都过了。
屏幕看着完全正常、探针 HUD 清清楚楚。

**根因**：`control/probe.py` 的 HUD 裁剪框写死成画面比例的 `(0.01, 0.03, 0.60, 0.62)`。
HUD 的宽度是**按 pt 固定**的（约 350），所以它在画面里的占比随屏幕宽度变：
375 pt 的 iPhone 竖屏上值列排到 **x≈0.91**，1180 pt 的 iPad 横屏只有 ≈0.55。
固定 0.60 在 iPhone 上把 `PT` 行第二个数和 `SIZE` 的「375 x 812」切掉 →
`parse_pt` / `parse_size` 都返回 `None` → `pointer_fraction()` 永远 None →
连续 4 次后 `_no_probe = True`，**整轮改走帧差却没有任何提示**。

**证据（同一帧）**：

| 裁剪 | `parse_size` | `parse_pt` | OCR 文本 |
|---|---|---|---|
| `(0.01,0.03,0.60,0.62)` | `None` | `None` | `'375x'`、只有 `'340.35，'` |
| `(0,0.02,1.00,0.70)` | `(375.0, 812.0)` | `(340.35, 334.87)` | `'375 x 812'`、两个数都在 |

**修法**：`_hud_box(w, h)` 按方向给右边界（竖屏整幅、横屏 0.62），下边界放到 0.70
（HUD 到 SCALE 行约 0.63）。另加一条：探针失效时 `progress("探针读不到，本次改用帧差
（精度会下降）")`，别再静默降级。

**回归测试**：`app/tests/test_probe_reader.py::HudCrop`，用真机帧
`app/tests/fixtures/probe-hud-iphone-500x1080.jpg` 断言能读出 `(375, 812)` / `340.35, 334.87`
（修复前这条会拿到 `None`）。

**教训**：探针"不报错、只是变慢变差"是最危险的状态——它让 iPad 上的好结果掩盖了
iPhone 上的完全失效。凡是"有真值就用真值、没有就回落"的分支，回落时必须留痕。

### 2.9 表中间留了个洞：内点离群，随机验证看不出来（2026-10-25 实测）

**现象**：同一台 iPad、两台 Mac 各跑一次自动校准。本机 **中位 15.3 px / 最大 36.6 px**，
另一台 **17.3 px / 138.1 px**。中位几乎一样，但两张表逐点对不上，最大差 272 px。

**根因**：**内点离群**——某一档只挪了一点点（或挪过头），而两侧档位都正常：

| 机器 | 坏点 | 本机值 | 正常趋势 |
|---|---|---|---|
| 本机 02:36 | BL x=600 | 0.5451（比 700 档的 0.4340 还远） | 应为 ≈0.37 |
| 另一台 10:00 | BL y=60 | 0.7918（比 30 档的 0.7662 还低） | 应为 ≈0.745 |

旧实现（0.9.38）只剪**表尾**（`while` 只比较最后两档），内点原封不动进表。
`units_for` 把表按 f 排序做分段插值，于是一段区间被彻底带歪：本机那张表
**tx≈0.55 的点击被算成 636 单位、实际落在 0.39，偏 246 px**。

**为什么验证没抓到**：`validate()` 每角只抽 4 个随机点（共 16 个），没抽到那一段；
中位 15.3 px 完全掩盖了一个 246 px 的洞。**中位误差不是表的合格证明。**

**修法（2026-10-25）**：`clean_table(points, sign)` —— 内点判**单调性**（某点和前后两档
都不同向就删该点），表尾沿用老规则。只判单调、不判斜率大小，是因为指针加速曲线本来
就不均匀（慢速档每单位位移更大），拿斜率卡会把正常档位当离群点删掉（试过，测试立刻挂了）。
修完本机 BL x `12 → 11` 档，同一批目标的最大误差 **246 → 23.8 px**。

> **0.9.48 起**：这种内点离群在**载入时**也会被 `clean_table` 剪掉（只改内存、幂等），
> 剪掉的点列在 `status.table.sanitized` 里。所以老档案不用为了这一个点重跑 25 分钟。

**复现性结论（两台 Mac，同一台 iPad）**：

| 角 | 位移一致性 | 说明 |
|---|---|---|
| BR x / BR y | **4–20 px** ✅ | 两次运行互相复现 |
| BL x / BL y | 272 / 54 px ❌ | 各自的坏点造成的，`clean_table` 后一致 |
| TL x / TL y | **72–101 px** ❌ | 低速档（150 单位）位移 47 vs 120 px，2.5 倍差 |
| TR x / TR y | 67 / 39 px | 同上，越靠近顶角越明显 |

顶角低速档不可复现，是 iOS 指针加速的**历史依赖**（上一段移动的快慢影响这一步的增益），
不是代码 bug——所以「换台机器再校一次」不能保证得到同样的表，这也是必须"当场测"的另一条理由。

### 2.10 真值 ≠ 终值：光标还在飞的时候读到的 PT 是中途位置（2026-10-25 实测）

**现象**：两台 Mac 各跑一次 iPad 校准，都没有发送失败、没有 AirPlay 帧告警，却各自产出一个坏点。

**排除过的原因**：

- 「不同 Mac 的 AirPlay 延迟不同」→ **不成立**。两台实测 188 / 182 ms，而
  `_settle()` = `max(0.55 + s/1000*0.25, 延迟+0.08)`，188+80=268 ms ≪ 550 ms，
  **延迟补偿根本没启用**，两台机器每一步实际等待时间完全一样。既然等待相同，结果就不可能
  因延迟而分叉。
- 「409 重发导致多走」→ 不成立：两台校准窗口内 409 计数都是 0。

**真正原因**：一次 `move` 不是"一下子到位"，而是分多条 HID 报告走完，光标要飞
**300–500 ms**。校准只等 0.59 s，余量 100–200 ms。把"取帧"(12 ms)和 OCR 拆开、
在**精确时刻**抓帧后离线识别，4 次试验里 **2 次在 450 ms 读到中途位置**：

```
move +150  起点 132.2   284ms:132.2   450ms:170.0   550ms:238.5   ← 450ms 是中途值
move +150  起点 132.2   228ms:132.2   300ms:134.6   450ms:187.6   550ms:238.5
```

这正好产出两类坏点：读到中途 → 位移偏小（另一台 BL y=60「几乎没动」）；
停车动作还在飞就开始测 → 两段位移叠加、偏大（本机 BL x=600「多走 173 px」）。

**关键认识**：探针给的是**真值**，但真值也分终值和中途值——系统当时确实在那儿。
所以 §2.8 说的"有真值就用真值"要补一句：**真值也要问对时机**。探针解决的是
"帧差算错质心"，解决不了"你问得太早"。

**修法（2026-10-25）**：探针 HUD 本来就有 `AGE`（距上次 hover 事件的毫秒数），
`probe.py` 一直没解析它。现在 `parse_age()` 读出来，`Calibrator.settle_pointer()`
发现 `AGE < 150 ms` 就再等 180 ms 重读，最多 3 轮：

- 停稳了就不多花时间（本机实测 0.59 s 时 AGE 已经 250–350 ms → 不触发）；
- 还在飞就等到停；读不到 AGE（老探针）按"已停稳"处理，保持旧行为。

### 2.11 验证在测「根本到不了的目标」，把好表判成 85 px（2026-10-25 实测）

**现象**：iPhone（500×1080）整轮校准顺利完成（探针全程没掉、四角都测完），
最后却报

```
验证中位误差 85 px 超过 80 px，已恢复旧校准表
```

新表被丢弃。可是用盘上那张表逐点量 12 个位置，误差只有 **1–16 px、中位约 6 px**。

**根因**：`validate()` 的目标从 `0.15–0.85` 均匀取，**没有先钳位**。
而底部锚定的 iPhone 底角停车点在 **y≈0.790**（`clamp_y` 会把更靠下的目标钳到停车点），
于是 `0.790–0.85` 这一段**永远到不了** —— 指针停在停车线，误差 ≈ `(0.85-0.79)*812 ≈ 49 px`，
再叠加 x 分量就是 50–85 px。16 个点里有几个落进这一段，中位就被顶过闸门。

**为什么 iPad 没踩到**：iPad 的停车点是 0.8625 > 0.85，取不到不可达目标。
**这个 bug 只在 iPhone 上出现**，之前所有 iPad 校准都正常。

**修法**：验证目标与 `move_to` 用同一个口径 —— 先 `self.d.clamp_y(corner, ty)`，
再用钳位后的值算单位和误差（`control/calibration.py::validate`）。

**教训**：**验证和实际执行必须用同一套可达性规则**。验证跑了一条生产中永远不会发的
路径（不可达目标），测出来的就不是表的精度，而是"目标本身没意义"。

### 2.12 指针压住 HUD：探针读不到，甚至可能认错数字（2026-10-25 实测）

**现象**（用户发现）：某些位置读数会失败或不可信。

**复现**：把指针停到 `(0.65, 0.23)`——正好是 HUD `PT` 行第二个数所在的位置——
连读 3 次 **3/3 全部返回 `None`**；同一批其余 5 个位置（含 `(0.30,0.23)`、`(0.50,0.39)`）
都是 3/3 一致。HUD 占屏幕左上约 `0.96 × 0.63`，**校准到顶角时指针一定会经过这里**。

**两种失效**：彻底读不到（返回 `None`，会走帧差兜底，问题不大）；
以及**认错数字**（部分遮挡，可能读成一个还能通过范围检查的错值）——后者会让错值
直接进表，正是前面 §2.9「内点离群」最可能的来源。

**修法**：`settle_pointer(expect=…)` 增加**合群性闸门**。采样时先按几何算出"应该在哪儿"
（`near`），实测读数偏离超过 `PLAUSIBLE_TOL = 0.30` 屏宽就丢掉重读，全都不合群就当没读到、
交给帧差兜底。**宁可少一个采样点，也不让一个错值污染整格。**

**结构性解法（推荐，尚未做）**：探针改成**二维码遥测**——一帧里编 `PT/EVT/AGE/SIZE`，
带纠错、抗局部遮挡，一次解码拿到全部字段，不再逐行认数字。这正是
`docs/pointer-tester/CONCEPT.md` 里 M0 的 **E2** 实验，探针 App 需要改版才能验证。
在那之前，合群性闸门是性价比最高的一道保险。

### 2.13 目标移动：拆成 2–4 段更准；但减少校准档位会放大尾部误差（2026-10-25 实测）

iPhone 500×1080，同一批 12 个随机目标、固定种子（`QUILEG_CALIB_BENCH=1` 的对照实验）：

| 变体 | 中位 | 最大 |
|---|---|---|
| 整段一次 | 14.5 px | 84.7 px |
| **拆成两段** | **10.7 px** | 83.9 px |
| **拆成四段** | **9.6 px** | 87.1 px |
| 表抽稀一半（步数减半） | 18.4 px | **178.1 px** |

- **拆段更准**（中位降 26–34%）：一次大位移经过指针加速曲线最陡的一段，抖动被放大；
  拆小后每段增益接近线性。所以 `Device.move_to` 默认改为**每条轴拆 2 段**
  （`MOVE_SPLIT`，用累计值分配，保证各段之和精确等于总量）。
- **减少档位是亏的**：中位只差 4 px，**最大误差从 84.7 翻到 178.1 px**。
  中位看不见这种退化 —— 校准该多测就多测，不要用"减少步数"换时间。

### 2.14 校准失败后，半成品表还留在内存里（2026-10-25，B1 顺带修）

- **代码依据**：`Calibrator._calibrate` 全程 `self.d.calib = data`（新停车点、上行距离、
  已经测完的角都写进去了）；旧实现失败时只把**磁盘上的** `calib.json` 还原，
  `Device.calib` 仍指向那份半成品。`Device.refresh_calibration()` 只比 mtime，
  它不会自己换回来。
- **后果**：今天四次失败之后，用户接着点的每一个动作都按半成品表算——而旧表一直
  好好躺在磁盘上。
- **修法**：`run()` 的 `except` 里 `_restore_live_table()`（优先 `d.reload()`，没有就
  直接读文件塞回 `d.calib`）。失败/取消都走这一条。

### 2.15 留帧诊断的 `Path` 没导入，NameError 被 `except` 吞掉（2026-10-25）

- `_dump_failed_frame()` 用了 `Path`，文件顶部却没 `from pathlib import Path`；
  外面包着 `except Exception: pass`（诊断不许影响校准），于是**「探针读不到就留一帧」
  从 0.9.41 加上起一次都没生效过**，现场也没有任何提示。
- 教训：诊断代码里的异常至少要有痕迹（这次补了 import）。写 `except: pass` 之前先想
  「这段代码本身会不会坏」。

### 2.16 续校档案不能跨屏幕 / 跨视频源拼（2026-10-25）

- `calib.wip.json` 里带 `w/h/source`；`take_wip()` 发现和当前屏幕（或 airplay↔uvc）
  对不上就**整份作废**并提示。几何变了拼出来的表比没有表更危险。
- **超过 24 小时**也作废（`WIP_MAX_AGE_H`）：§0.0.3-4 已经证明同一张表会「时好时坏」，
  因为指针速度/加速状态会变；把昨天量的角和今天量的角拼起来，等于把两种状态缝进一张表。
- 落盘用 `临时文件 + os.replace` 原子替换（`calib.json` 有两个写者的坑见 §0.0.3-6）；
  失败、取消都**不删**，只有「四角都测完写进正式表」或「闸门判定重跑」才删。

### 2.17 `job.error` 只有字符串，结构化信息全丢（2026-10-25）

- `JobQueue` 把异常压成 `str(exc)`，界面再想拿「哪一类失败、从哪个角继续」就只能猜。
  现在 `Job.exc` 保留原始异常，校准器把 `Failure` 挂在异常上
  （`attach_failure`），界面优先读它，读不到才按文案分类。
- 顺带：GUI 里 `fit_buttons` 会把一组按钮拉成**等宽**，标签一长（「继续校准（从 TR 开始）」
  13 个字）整排就会被挤出向导。续校按钮不进 `fit_buttons`，并按
  `measure_width()` 逐级降级成短标签（实测 UI 放大到 1.3 倍时四颗按钮 725 px > 720 px）。

### 2.18 探针 App 侧三个坑（2026-10-26，Pointer Tester 0.1.0 出包时）

1. **`@objc` 方法不能叫 `release`**：首页入口卡片把「按下缩放」的回弹方法起名 `release()`，
   绑到 `.touchUpInside` 后一按就 **SIGSEGV**——Objective-C 选择器 `release` 与 UIView 的
   内存管理方法同名，运行时自己递归调用（崩溃报告 `recursionInfoArray` 深度 16321）。
   改名 `restoreScale()` 即好。同类危险名：`retain` / `dealloc` / `copy` / `init…`。
2. **`String(format:)` 里内联三元会被推成 `Int`**：
   `String(format: "P1,%.2f,%.2f,%.0f,%.0f,%.0f", x, y, age < 0 ? 999999 : age, w, h)`
   输出的第三个数**永远是 `0`**（`%.0f` 按 double 读到了 Int 的错位字节）。
   先落成 `let ageOut: Double = age < 0 ? 999_999 : age` 再传。
   这个 bug 从 0.9.x 的探针一直带到现在：二维码里 `age_ms` 恒为 0，宿主 `probe.read_state()`
   拿到「指针刚动过」，停稳判断只能靠文字 HUD 兜底。
3. **xcodegen 的 `info:` 段会和手写 `Info.plist` 打架**：生成时直接覆盖，版本号写死成 1.0。
   现在 `project.yml` 不再有 `info:`，`Info.plist` 是唯一来源，版本用
   `$(MARKETING_VERSION)` / `$(CURRENT_PROJECT_VERSION)`。

4. **`touches.count` 数的是「本次事件新增的手指」**：画布用 `if touches.count >= 2` 判断双指轻点，
   第二根手指落屏时那次事件的 `touches` 只有 **1**，条件永远不成立 —— 0.1.0 实测「双指轻点没反应」。
   要看 `event?.allTouches?.count`，或者自己维护活跃触点集合。已加 UI 回归测试
   （`UITests/CanvasExitTests.swift`，3 个用例全过）。
5. **XCUITest 遇上 150 ms 定时器 = 每个操作等 30 秒**：画布每 150 ms 刷新文字，
   主线程永不 idle，`app.launch()` / `twoFingerTap()` 都要等到超时才继续（实测 3 个用例 100 秒）。
   测试里用 `PT_UITEST=1` 关掉 ticker 之后，同样的用例 5–9 秒跑完。

6. **UI 测试别走「调试直达」，要走真实入口**：为了截图方便有个 `-ui canvas` 启动参数，
   直接 present 画布——它**绕过了首页挂退出手势的那段代码**，于是两个退出用例都“失败”，
   而 App 其实是好的。测试改成「启动 → 点 `enterTest` → 画布 → 手势退出」后全过。
   调试钩子只用于截图。
7. **给冻结的旧界面加功能，加在门外**：用户要求画布回到旧版且「一点都不要改」。
   首页当 root，画布用**全屏 modal + 自定义转场**（`CanvasTransition.swift`）从右侧滑入；
   退出由 `CanvasTransitionController` 往画布的 view 挂手势，画布源码一行不动。
   这样状态栏 / Home 指示条 / 屏幕边缘手势仍由画布自己决定。
8. **右滑退出用 `UIPercentDrivenInteractiveTransition`**：`.began` 时先建交互对象再
   `dismiss(animated:)`，`.changed` 里 `update(translation/width)`，`.ended` 里按
   「>30% 或速度 >600」决定 finish/cancel。全屏 pan 不怕和校准打架——校准全程只发
   hover（`move`），从不 press/click，产生不了触摸。
9. **XCUITest 的秒数不是性能数据**：`app.launch()` 到首页 6–8 s、点按钮到画布 1.7 s，
   看着像 App 慢；插 `NSLog` 量 App 内部：**tap → 动画开始 15 ms、tap → 画布呈现 348 ms**。
   多出来的时间是 XCUITest 等 quiescence + 取快照（画布 0.2 s 定时器还会加重）。
   要评性能，用 App 内打点或 Instruments，别拿测试耗时。
10. **「没改」要用像素证明**：`git worktree add /tmp/old <commit>` → 用旧提交构建 →
   同一个模拟器、同一分辨率各截一张 → `PIL.ImageChops.difference` 对比。
   注意**等系统 UI 稳定**：Home 指示条要几秒才自动隐藏，4 秒截会多出 6449 px 的假差异，
   等 9 秒就是 0 差异（3,162,132 px 全同，最大通道差 0）。

> **改画布 UI 的廉价回归法**：不用真机——模拟器截图 → 缩到 500×1080 + JPEG q72
> （等价 AirPlay 投屏帧）→ 喂 `control/probe.read_state()`。二维码路径与「涂黑二维码」
> 的文字回落各跑一次，就知道契约有没有断。

> **出包的签名陷阱**：本机 ASC API Key（`MysqlBackup-CI`）能读 ASC、能建描述文件、能校验包，
> 但**没有云托管分发证书权限**，`xcodebuild -exportArchive` 自动签名会报
> `Cloud signing permission error` + `No profiles for ...`。改成手动签名（本机
> Apple Distribution 证书 + `pointer-tester/profile.sh` 用 API 建的 `IOS_APP_STORE` 描述文件，
> 见 `ExportOptions.manual.plist`）就通了。

### 2.19 拿几何估计去否掉探针真值 → 残表还能过闸门（2026-10-26 实测）

**背景**：`age` 修好之后（§2.18-3），`settle_pointer` 的「停稳」判断第一次真正生效。
第一次完整校准（10:01–10:24，iPhone 500×1080）结果：

```
校准完成：中位 17.9px，最大 265.8px        （上一张：9.75 / 107.8）
```

**两个独立的问题叠在一起**：

1. **合理性检查方向反了**。`settle_pointer` 用几何估计 `near`（固定 731/1611 单位/屏外推）
   去否掉探针读数，超 0.30 屏就判「偏离预期、重读」。可探针给的是**二维码解出来的真值**，
   估计只是粗算——档位越大估计越偏，于是 TL 的 150/300/600…1100 全被判偏离，退回帧差。
   帧差和探针混在同一张表里，比例尺对不上，`clean_table` 再把「非单调」的档位当离群点剪掉：
   **TL x 12 档只剩 4 档（覆盖 37%）**。
2. **闸门只看中位数**。17.9 px 中位漂亮，265.8 px 的单点没人管；残表照写。

**修法**

- `probe.read_state()` 多返回一个 `source`（`qr` / `ocr`）：二维码是带纠错的整帧编码，
  解出来就是真值；只有 OCR 认数字才可能串行、被指针压住。
- `settle_pointer` 对 `source == "qr"` **不再做合理性检查**（OCR 仍然做）。
- 闸门加两条：
  - 单点误差 > **250 px** → 判失败（表里有断层）；
  - 任一轴覆盖 < **40%** 屏 → 判失败（表外全靠外推）。40% 这个数是因为底角 y 表
    正常也只到 0.48，用 55% 会误伤好表（单测里当场就炸了）。
- `_GATE_HINTS` 加上「验证最大误差」「覆盖」，让界面把它归成精度闸门类。

**修完的验证**：单独测 TL 复现 → `TL x 6 档、覆盖 86%`（修之前 4 档 / 23%），
值也连续了（20→0.141, 40→0.183, 60→0.225, 150→0.42, 300→0.729, 1100→0.998）。

**教训**：任何「拿估计去否决测量」的代码都要先问一句——**哪个是基准**。
另外，验证的中位数能掩盖单点崩塌，闸门必须同时看覆盖和最大误差。

**表尾平台（同日第二个坑）**：指针快的时候，450–1000 档全贴在边缘（x≈0.99），
读数平台化后被单调性清理当「内点离群」剪掉，只剩 300 → 1100 一个长段；0.8 附近的目标
被外推过头、直接撞边缘（验证里 3 个 ~100 px 的点）。修法：**先裁表尾平台、保留平台起点**
（代表「推到这么多单位就到边」），再跑单调性清理。修完验证：**中位 10.4 px / 最大 21.1 px**
（16 点，没有一点点撞边缘），独立复测 5.8 / 8.3 px——上一张好表是 9.75 / 107.8。

**链路宽限（用户现场反馈，同日）**：6 次快速重试（≤20 s）对「板子状态灯闪一下又自己恢复」
是不够的——人不在旁边时，校准已经终止，回来只剩「开始校准」，十几分钟白跑。
现在 6 次之后进入**最多 3 分钟的等待链路宽限**：每 5 秒试一次命令 + `ensure_ble()`，
状态行显示进度，恢复后原地继续。判定哪些异常算「链路」的规则见 `_is_link_error`：
409/408/429/5xx、URLError、TimeoutError、ConnectionError；我们自己的 bug 立刻抛，不等。

### 2.20 iPhone 也被写进 park="bottom" → 屏幕底部 22% 静默不可达（2026-10-26 实测）

**现象**（用户现场）：13:00 重跑校准之后，iPhone 上 `y > 0.78` 的点击/移动全部落在
`y ≈ 0.77`，而且 MCP 返回的模型位置仍是目标值 —— 只有 `pointer_position(detect=True)`
才看得出偏差：

```
move(0.5, 0.95)  -> model (0.500, 0.950) / detected (0.495, 0.778) / err 185.3 px
计算器 7+8=      -> "="（y=0.894）点成了 "+"，显示 "7+8+"
备忘录「新建」    -> （y=0.938）打开的是列表里已有的一条笔记
```

**根因（三个独立缺陷叠在一起）**：

1. `control/calibration.py` 新校准**无条件**写 `data["park"]="bottom"` + `park_lift`
   （= 12% 屏高，为避开 iPad 程序坞），iPhone 也照写 —— 底角停车点从 0.97 抬到 0.79；
2. 同一处 y 表护栏 `s > 0.85*est_h → break`（防指针碰底边）在 iPhone 上也生效，
   `1000/1400/1500` 三档全没测：TL/TR y 表只到 **0.63**、BL/BR 只到 **0.735**；
3. `control/device.py` 的 `clamp_y` 以 `ref_y` 为界钳位，于是 0.79 以下的目标被压回
   0.79，`units_for` 再外推出 0/负数单位 —— **一条纵向命令都不发**，指针留在停车点。

**为什么验证没抓到**：`validate()` 的目标先 `clamp_y` 再算误差，0.85 以下那一段
（本来就到不了）被当成「可达目标」测，中位仍是 **7.15 px**。中位数看不见一个洞。

**修法（0.9.47）**：把「形态」变成显式概念，写进档案（`form: phone|tablet`）：

| | 手机（无程序坞） | 平板（iPadOS 26） |
|---|---|---|
| 归位 | `home`（老路径） | 底部锚定（绝不碰顶边） |
| 底角停车点 | 不抬（ref ≈0.97） | 抬到程序坞上方（ref≈0.86） |
| y 表护栏 | 不截断，一直测到指针真的贴边 | 离底 0.86 / 离顶 0.12 就停 |
| 钳位 | 不钳（`park_lift=0` 时 `clamp_y` 直接放行） | 钳到停车点（程序坞带本来就没有表） |
| 验证目标 | 抽到 **0.95**、**不钳位** | 抽到 0.85、钳位 |

形态怎么定（0.9.47）：**① 环境变量 > ② 镜像长宽比 > ③ 被控设备选择 > ④ 现场探程序坞**。

- 比例是客观的（手机 0.46 / 2.16，平板 0.69–1.44）：平板比例直接判平板，选了 iPhone 也以比例为准；
- **手机比例两头都可能**（iPhone、Android，也可能是 letterbox 的 iPad —— iPad Air 11" 出现过
  500×1080），这时看「设置 → 被控设备」选的是 iPhone 还是 iPad（0.9.47 把这一项拆成了两个，
  见 §2.20 末段）；
- 两样都不知道（老设置 / 非 Apple 平台）才**现场探一次程序坞**（指针贴底 → 抬 260 单位 →
  比底部中央带的变化像素）。真机实测：本机 iPhone **0 px / 63375 px → 无程序坞**。

`QUILEG_DEVICE_FORM=phone|tablet` 可强制覆盖。另外新增闸门 `bottom_unreachable()`：
手机的 y 表摸不到 0.90 就**拒绝写表**。

**教训**：

- **同一套「避开系统 UI」的补偿不能无差别套到另一种设备上** —— 上抬停车点对 iPad 是
  必需的，对 iPhone 就是拿走屏幕底部 22%；
- **验证必须和实际执行用同一套可达性规则，但闸门要单独看覆盖**：钳位后的验证永远测不到
  被钳掉的那一段（这条与 §2.11 是同一类错误的正反两面）；
- 老档案没有 `form` 字段时，`form_of()` 用「有没有 park」反推；`calibration_status`
  现在会直接给 `warnings`（含「底部 XX% 没有映射」），AI 排障先看这一行。

**证据**：`~/Library/Application Support/HIDBridge/app-ui.log` 12:48:05 `BR y=600` 之后
直接跳到「底部锚定：顶角上行」、13:00:22 `TR y=600` 之后直接「四角已测完」；
13:02:59「校准完成：中位 7.15px，最大 26.2px」；13:00 那份 `calib.json` 的
`park_lift=189.2`、`refs.BL=[0.0367,0.7902]`、TL y 表止于 `[600, 0.6309]`。

**同一轮的产品改动（0.9.47）**：「被控设备」从 `ios`（iPhone + iPad 一项）拆成
**iPhone / iPad 两项**，入口也搬到**视频上方工具条最左**（「被控 XXX ▾」，点开即切；
这个选择同时决定键盘策略与校准形态，藏在设置里没人会主动去改）。理由不止校准：iPadOS 有 ⌘Tab 与多任务、iOS 没有（2026-10-22 实测
`cmd+tab` 在 iPhone 上完全无反应）。所以 `keymap_default.json` 里 iPhone 不再放行
`gui+tab` / `gui+shift+tab`，`switch_app` 动作在 iPhone 上返回「不支持」，iPad 照旧。
老设置 `ios` 自动迁移为 `iphone`，老 `keymap.json` 里的 `ios` 覆盖也会迁进 `iphone`（不丢配置）。

**回归**：`app/tests/test_calib_form.py`（22 条：形态判定 / 程序坞探测 / 手机不写 park /
y 表到底 / 平板仍让开程序坞带 / 闸门）；`test_move_clamp.py` 补「无程序坞不钳位」；
`test_device.py` 补「手机不做中部停靠」。真机验收：计算器 `7+8=` 得 15、
备忘录右下「新建」出空白笔记。

### 2.21 把校准当「必选项」＝把设备适配做成无底洞（2026-10-26 口径）

**问题不在工具能力，在口径。** 0.9.47 之前，文档、`status.calibrated`、向导文案三处都把
「有一张四角表」当成能干活的前提：

- `AI_GUIDE` §0：`calibrated=false` → 「**停止**，先跑校准向导，不要盲点」；
- `status()` 把 `calibrated` 摆成健康位，`calibration_request` 只有「请用户跑 25 分钟」一条路；
- 更危险的是代码：没表时 `units_for()` 返回 **0 单位**，`move` 空转、`click` 点在原地，
  **全程静默**——AI 会以为点过了。

后果是每遇到一台新设备、一个没测过的分辨率，都得让用户陪着跑 15–30 分钟向导。设备是无限的，
这条路走不通。

**现在的口径（0.9.48）**：校准是**可选的加速项**，作用只有一个——把「每次动作 1–3 次闭环」
压成「一次开出」。

| | `positioning=table`（有表） | `positioning=visual`（没表） |
|---|---|---|
| 怎么走 | 四角归位 + 分段表，一次开出 | 移动 → 找指针 → 按实测位移修增益，1–3 轮 |
| 精度 | 5–30 px | 10–40 px |
| 每次动作 | 基准延迟 | 多 2–6 s |
| 适用 | 小图标、密集列表、拖拽/长按、批量连点 | 一次性设备、临时机型、点大按钮 |

**三条失败必须响亮**（这是「可选」能成立的前提）：

1. 读不到指针（画面在动 / 指针太小 / 被隐藏）→ 抛错「视觉定位读不到指针…」；
2. 中途读不到 → 抛错「已停在未确认位置，请重试」；
3. 收敛不了（增益不稳定）→ 抛错「视觉定位没收敛（N px，M 轮），建议校准」。

**宁可失败，也不在一个没量过的位置上点下去** —— 静默点偏比失败更糟（§2.20 就是这么来的）。

**边界（别过度承诺）**：拖拽/滚动/长按中途停不下来，视觉模式下只是「能用但更慢更粗」；
帧差找指针本身有已知盲区（hover 只有 ~90 px、画面里的灰圆会被误判成指针）。
要稳定精度还是两件事：**Pointer Tester 探针**（真值读点，[TestFlight 装一个](https://testflight.apple.com/join/zAXDqJsX)，iOS 17+）
或**一张表**。

**教训**：一个能力被写成「前置条件」，就等于给自己加了一维无限的适配矩阵；
写成「可选 + 诚实降级」，适配成本才回到可控。文档里的「必须先 X」要定期回看——
它往往比代码更早把路堵死。

### 2.22 `ACK ≠ 送达`：链路抖掉的 2 秒，吃掉 26 分钟的校准（2026-10-26 实测）

**现象**：一轮校准四角全部测完、表也写了，验证却报「最大误差 343 px（TR 目标 [0.216, 0.393]）
超过 250 px → 旧表已恢复」。日志里这一轮有 **6 次 `board gone`**（15:33:36 … 15:45:02 …），
其中 15:45:02 正好落在验证窗口；同一台设备 13:00 那轮是 **0 次**断链。

**根因**：`move` 的 `{"ok":true}` **只代表报告写进了 BLE 缓冲**，不代表手机收到。
链路在那一瞬间抖一下，报告丢了、指针没动，而工具链看到的是成功 —— 于是这个点偏 343 px，
被闸门判成「表里有断层」。**这种失败没有异常可捕**，只能靠多试几次兜住。

**四层容错**（前两层 0.9.44 起，后两层 0.9.49 起）：

1. 每条命令重试：6 次快速（1.5→3→6 s）+ 最多 3 分钟等链路（`_retry`）；
2. 断点续校：每测完一个角落 `calib.wip.json`，失败只丢当前角；
3. **单点重测**：验证里某个点偏 > 250 px，先重测这一遍再判（~10 s）；
4. **整轮重验**：准确率闸门不过时重跑一轮 16 点再判（~2 min）。

第 4 层只对准确率闸门生效；「档位不足 / 覆盖不够」这类形状闸门重跑没用，不浪费那 2 分钟。

**同一版顺手补的**：表里没有映射（目标被 `clamp_y` 钳住）且被控设备是 **iPhone** 时，
那一段改走闭环 —— 老档案底部 21% 没映射也能点到底部按钮，不必等重校。
**iPad 保持钳位**：那里的钳位是在让开程序坞带，用闭环硬点会命中程序坞。

**教训**：硬件链路层的「成功」只能当**弱信号**用。凡是「收不到就会静默错」的地方，
都要在语义层补一次验证（落点、画面、覆盖率），而不是指望 ACK。

### 2.23 Pointer Tester 网页版：能当探针，但底部 6% 是死的（2026-10-26 实测）

> **怎么装**：原生版走 TestFlight 外部测试 <https://testflight.apple.com/join/zAXDqJsX>（已过 Apple 审核，iOS 17+；不联网、

**做法**：把探针做成 PWA（`pointer-tester/web/`，托管在
`https://jianghui1974.github.io/Quileg-HID/probe/`），分享 → 添加到主屏幕 → 独立窗口打开。
好处是**零安装**（不用 TestFlight/开发者证书），坏处是两条 iOS 限制。

**1. 视口比屏幕矮 50 pt**（iPhone 375×812，iOS 26，standalone + `viewport-fit=cover`）：

```
VIEW 375 x 762 ⚠    ← window.innerWidth/innerHeight
```

实测沿 x=0.5 从 y=0.90 扫到 0.98（`probe.read_state()` 读回）：

| 目标（屏幕 pt） | 读回 | AGE |

**二维码（19:47 补上，已真机验过）**：页面右下角每 80 ms 重画一次

**结论（口径）**：
- **日常真值 / 验证落点** → 网页版够用，还免安装；
- **停车点**（0.9.50 起）网页版够用：`measure_ref()` 三道闸门（探针要求 AGE≤1200 ms

- **整张表**：**iPhone 上量不出来、iPad 上可以**。
  - **iPad（1554x1080 横屏）实测通过**：中位 **13.75 px**、最大 65.2 px（原生探针那张是
    15.3/36.6），中途断链 136 s 也扛过来了。原因：平板形态把停车点上抬到 0.86（避程序坞），
    四个角都不在死区；顶部停车点会被 `tune_top_park` 自动下移（TR 从 0.048 让到 0.117），
    表以它为基准仍然自洽。
  - **iPhone 上三轮完整校准都在验证阶段被闸门拒绝**（单点偏 267 / 359 / 403 px，重验也没过，

### 2.24 打包后 `corner_profiles.json` 找不到 → 圆角模型静默失效（2026-10-26 实测）

**现象**：用网页版探针跑校准，每一轮都停在 `BR: 测不到停车点`（探针在屏幕底部死区、
帧差又认错），本该兜底的**圆角几何模型**没有生效。

**根因**：`corners.py` 用 `Path(__file__).with_name("corner_profiles.json")` 找档案。
PyInstaller 把模块冻进包里后 `__file__` 指向包内，这个路径落空；真实文件在
`Contents/Frameworks/control/corner_profiles.json`。`except` 把 FileNotFoundError 吃掉、
返回 `{}` → `profile_for()` 恒 None → **打包版的圆角模型一直不存在**（源码运行正常，
所以单测与手工验证都发现不了）。

**修法**：按 `ocr.py` 的多目录搜索（`__file__`、`_MEIPASS`、`Resources` 及其 `control/`），
外加 `HIDBRIDGE_CORNER_PROFILES` 显式覆盖；测试里模拟 `sys.frozen` + `_MEIPASS` 复现。

**教训**：**「读不到配置文件就当没有」的降级逻辑，会把打包问题变成静默的功能缺失。**
凡是这种 `except: return {}` 的地方，都要有一个「在冻结点也能找到」的路径，并且至少
在日志里留一句——否则它只会在你最需要兜底的那一刻消失。

### 2.25 往弹窗正文里加卡片 → 底部按钮被裁到窗口外（2026-10-26 实测，0.9.52 回归）

**现象**（用户现场）：校准向导里**看不到「开始校准」**。窗口右下角只剩半截分割线，
拖不动、也没法滚动；只能点右上角关闭。0.9.52 之前是好的。

**根因（三条叠在一起）**：

1. `CalibrationDialog` 的窗口高度写死 `min(760, int(700 × fonts.scale))`（`dialogs.py`），
   而 0.9.52 在正文里加了「探针工具（免安装）」卡片 ≈ **100 px**；
2. `_footer_bar()` 在正文**之后** `pack`：Tk 按顺序分配空间，窗口不够高时
   **最后 pack 的那个被挤出窗口**——正好是动作栏；
3. 正文里 `tk.Text` 没写 `width`，Tk 默认按 **80 字符**要宽（≈800 px）——一旦按内容定宽，
   窗口会被撑到 970 px 宽。

**实测数据**（`artifacts/2026-10-26-calib-wizard-fix-*.png`，模块级脚本量 `winfo_rooty`）：

| UI 缩放 | 修前窗口 | 内容需要 | 「开始校准」底边 | 被裁 |
|---|---|---|---|---|
| 1.0 | 640×700 | 801×777 | 772 > 700 | **72 px** |
| 1.3 | 720×760 | 1015×991 | 986 > 760 | **226 px** |

**修法**：

- 动作栏改成 `_footer_bar(..., side="bottom")` 并在正文**之前** pack —— 先占住底边，
  窗口不够高时被压的是弹性的日志区，按钮永远在窗口里；
- `_fit_and_center()`：窗口高度按 `winfo_reqheight()` 定（下限仍是 700），上限 `屏幕高 − 120`；
  还塞不下就把日志从 7 行往下缩（最少 3 行）；
- 正文折行宽度跟着窗口宽度走（`_apply_wrap`），扣掉外框/内边距约 92 px ——
  写死 560 时 UI 放大后每行都留一截空档，多出来的行正好把日志挤没；
- `Text(width=1)`：宽度交给 `pack(fill="x")`，避免默认 80 字符把窗口撑宽；
- 顺带：「地址已复制」并到按钮同一行、URL 折行上限，省掉两行高度。

**教训**：

- **弹窗里加内容，先问「窗口高度是写死的吗」**。写死 + `pack` 顺序 = 后加的东西把按钮顶出去，
  而且**没有任何报错**，用户只会说"按钮不见了"。
- 动作栏要**先 pack**（`side="bottom"`），让弹性区（日志/列表）承担压缩；
  反过来做，压缩的永远是最后一个 pack 的控件。
- 「按内容定高」一旦开了口，就得同时管住**宽**：`Text` / 长 URL / 未折行的 Label 都会
  反向把窗口撑大（本例 640 → 970）。

> 回归：`app/tests/test_calib_dialog_layout.py`（4 条，真 Tk 建窗量几何，1.0 / 1.15 / 1.3 三档 +
> 「窗口要装得下正文」）；无窗口服务器时自动 skip。全套 **488 passed**。

### 2.26 动作后的截图晚一整步：AI 会把「已生效」当成「没生效」（2026-10-27 实测，0.9.54）

**现象**（iPad 真人流程）：按 Esc 关掉 Spotlight —— 返回的截图里 Spotlight 还在；
敲退格删掉字符 —— 返回的截图里字符还在选中。AI 判「没生效」，又按了一次：**真多删了一个字**。
同一轮里 ⌘Tab / ⌘H / ⌘Space 都被判成「不支持」，其实都生效了。

**根因**：AirPlay 只在画面变化时发帧。`click_verified()` 的动作是：
`before = frame()` → 发 `click` → `wait_stable()` → `after = frame()`。
动作刚发出时，`frame()` 拿到的仍是动作前那一帧；`wait_stable()` 看到「两帧一样」就判
「稳定」，于是 `after` 就是 `before` → `changed_px=0`。**「没有新帧」被当成了「没有变化」。**

**修法（0.9.54）**

- 服务端 `/api/frame.jpg` 回 `X-Frame-Age-Ms` / `X-Frame-Time`（帧的真实时间）；
- 客户端 `_fresh_after(before, since)`：等到**时间戳比动作前新**的帧才返回，超时才认输并
  标记 `fresh=false`；老服务端没有时间戳时立刻返回（不白等 1.3 s）；
- `click` / `key` 返回 `fresh` / `frame_age_ms`，摘要分三种情况写：
  画面有变化 / 新帧到了但没变化 / 没等到新帧；
- 取基准帧前先 `wait_stable()`，避开程序坞弹出/收起动画（它也会被算成「画面变了」）。

**教训**：**「没等到证据」和「证据说没有」是两件事。** 所有「等一会儿再判断」的代码，
都要能区分「超时」与「确认」。

> **0.9.54 的补丁（0.9.55）：新时间戳 ≠ 新内容。** 只等「时间戳更新的帧」还不够——
> 时间戳是**帧到达**的时间，画面内容还压在投屏管线里（AirPlay → GStreamer → JPEG，
> 0.2–0.5 s），转场更长。实测：计算器按 AC（15 → 0）、主屏点 Safari 图标、
> Safari 点「+」，都拿到了「新的一帧、但内容还是旧的」→ `changed=False`，
> `click_text` 因此双击了图标。
> 现在改成三步：**等内容真的变（最多 1.2 s）→ 等转场结束 → 用稳定后的帧算变化**；
> 另加 `changed_any_px`（含状态栏那一条），顶部工具栏（Safari 的「+」在 y≈0.07）
> 的动作才不会被「跳过顶部 6%」的规则判成没变。

### 2.26a `changed=false` 也不是「一定没生效」（2026-10-27 实测）

0.9.55 之后 `changed` 已经是「等内容真的变 → 等转场 → 用稳定帧算」，但仍有两类**假阴性**：

| 动作 | 现象 | 原因 |
|---|---|---|
| 点 Safari 地址栏（聚焦） | `changed=False`，其实光标已进去 | 光标/焦点环只有几十 px，低于 `min_px=60` 与阈值 |
| 点自动补全里的网址 | `changed=False`，随后页面自己加载完了 | 网页导航 >1.2 s（`changed_after` 的等待上限），截稿时页面还没换 |

**用法**：`changed=false` 只代表「1.2 s 内没捕捉到变化」，不等于没生效。判失败前先
`ocr_timeline()`（它会说「这块刚出现 / 一直没动」）或隔 1 s 再截一张；连续两次都为空、
且目标在顶部/底部系统带里，才判失败。

### 2.27 程序坞是我们自己扫出来的（2026-10-27 定位）

用户反馈：鼠标一到底部，程序坞就弹起；它没有文字，OCR 看不到，收起时又让画面变化。

**根因在归位方式**：平板档案是 `park="bottom"`，`goto_corner()` 每次动作都先把指针
`move ±4000 4000` **按到底边**、停 0.45 s，再从底边上行到目标。也就是说**每一次动作都会
在屏幕底边停留一次**——这正是 iPadOS 弹程序坞的条件。它不是「用户手滑」，是我们自己干的。

**已做**

1. 取基准帧前等画面安静（`settled`），程序坞的弹出/收起不再被算成点击效果；
2. **`dock_visible`（0.9.56）**：归位时在「压到角」和「上行之后」各取一帧，只比屏幕最下面
   那一条（y>0.86）。实测两种结果都见过 —— 中屏 / y=0.80 / y=0.86 的目标是 `false`
   （底边只差 71–282 px，指针自身），而 Safari 顶部「+」那一次是 **true（底边变化 68 294 px）**，
   摘要直接写「程序坞被拉起来过」。差别在于程序坞**有没有在动作时还挂着**。

**可选的做法（未做，按需挑）**：

1. **底边停留时间压到最短**：到角后立刻上行，只在需要精确 y 原点时才多停；
2. **程序坞检测**：动作后比一下「底边 12% 那一条」在归位前后有没有变——变了就是程序坞被
   拉起来了，返回 `dock_visible: true`，AI 就知道这一段是系统 UI，不是 App 内容；
3. **OCR 锚点**：在程序坞里放一个图标带文字的 App（小红书就是现成的），
   OCR 读到它就知道「程序坞已弹起」。能做，但依赖图标、依赖 OCR 识别率，
   不如第 2 条直接看底部那一条的像素；
4. **从根上避开**：把「顶部停车点 + 上抬的底部停车点」改成「只用左右两条边 + 实测 y」，
   不再碰底边——最彻底，但要重做归位与校准的形态。

### 2.28 OCR 降级成 `.fast`：不是签名问题，是 ANE / mach-lookup 被掐（2026-10-27 定位）

**现象**：`ocr-text` 每次调用都在 stderr 打

```
ocr: accurate 不可用，已降级为 fast（unknownError / Foundation._GenericObjCError 0）
```

同一张图：降级版 7 个 block、中文乱码（`IIt*1241> •,-, 2027 *iTIX`），
正常版 20 个 block（`阅读7.6万 赞1234`）。MCP 那侧完全看不到这句 —— 只会觉得「这张图认不出来」。

**根因**：`.accurate` 走 **ANE**（TextRecognition → e5rt / ANEServices）。它要两样东西：

1. **mach-lookup** 到 ANE / TextRecognition 服务；
2. 能读（首次能写）`~/Library/Caches/vision_arm64`（编译好的 `.e5` 模型）。

被掐掉任一条就抛一个**没有信息量的** `_GenericObjCError 0`，`.fast` 仍可用 →
helper 按设计降级。Intel 上是同一类失败的另一种错误码（`CRImageReaderError 9`，见 §2.3）。

**30 秒证伪/证实**（不依赖手机，随便一张 JPEG）：

```bash
# 正常：engine=accurate / degraded=false
control/bin/ocr-text shot.jpg | python3 -c 'import json,sys;d=json.load(sys.stdin);print(d["engine"],d["degraded"],len(d["blocks"]))'
# 模拟「受限进程」：一秒内降到 fast（复现用户报的那条 stderr）
sandbox-exec -p '(version 1)(allow default)(deny mach-lookup)' control/bin/ocr-text shot.jpg
```

实测（2026-10-27，M1 Pro / macOS 27.0.1）：

| 场景 | 结果 |
|---|---|
| 普通终端，包内 `Contents/Frameworks/control/bin/ocr-text` | `accurate`、21 blocks，3/3 正常 |
| 同一份文件改名 / 重签名（adhoc、DevID+runtime+entitlements） | 全部 `accurate` —— **签名无关** |
| 同一份包内文件 + `sandbox-exec -p '(…)(deny mach-lookup)'` | `fast`、14 blocks + 用户报的那句 stderr，一条命令复现 |
| 开发版（同源码新编）在同样 `deny mach-lookup` 下 | 同样 `fast` —— 版本也不相关 |
| DSH 会话的 seatbelt 沙箱 | 包内那份降级；同一沙箱里**旧开发版**恰好还是 `accurate`（差异没定到具体规则，可能是 mach 白名单 / 已缓存的编译产物）。**所以「包内 vs 开发版」本身不是判据** |
| `HOME=` 空目录（没有 `vision_*` 缓存、又要现编译） | **卡住不返回**（>60 s），MCP 侧 30 s 超时 |

> **教训**：看到「包内二进制 vs 开发版行为不同」先别怀疑签名/构建参数——
> 把**执行环境**换掉（同一个文件放在同一个 shell 里、换成不沙箱的终端）再比一次。
> 这次真正的变量是「哪一层沙箱/哪份 HOME」，签名只是恰好和它们一起变。

**已经做的（0.9.63）**：

- helper 在 JSON 里回 `engine` / `degraded` / `degraded_reason`，stderr 另打一行
  `OCR_DEGRADED engine=fast reason=…`；`.accurate` 失败先**原地重试一次**再降级；
- `ocr_jpeg()` 把三个字段带进结果，并**只 WARNING 一次**（每帧都刷会把日志淹掉）；
- MCP `ocr()` 摘要顶部加 `⚠️ OCR 引擎已降级…`，`click_text` 找不到目标时也提示
  「可能是引擎降级，不是目标不存在」；GUI 的 OCR 面板同样在日志里留一行；
- 老 helper（只在 stderr 说一句）仍然能识别成降级，不用等用户升级 App。

**自查清单（以后遇到「OCR 变差」按顺序走）**：

1. 看返回里 `degraded` 是不是 true，`degraded_reason` 写了什么；
2. `env -i` 干净环境再跑一次（排除调用方塞的环境变量）；
3. 确认不是 Intel / Rosetta（§2.3）、不是 `HOME`/缓存缺失；
4. 还降级就查「谁允许了 mach-lookup」：终端沙箱、`sandbox-exec`、IDE 的沙箱插件、
   系统级 MDM 配置都可能掐掉 ANE；
5. **别**去重签名、别改 entitlements、别重装 App —— 这张表里没有一条是签名引起的。

### 2.29 写 Wi-Fi 报 `[Errno 2] could not open port …`：端口改名了（2026-10-28 客户现场定案）

**现象**：设备初始化第 5 步点「写入并应用」直接红字

```
写入失败：[Errno 2] could not open port /dev/cu.usbmodem1234561:
[Errno 2] No such file or directory: '/dev/cu.usbmodem1234561'
```

同时顶栏 `板子 离线` / `BLE 未知` / `投屏 无信号`。**这不是 Wi-Fi 或密码的问题** ——
`open()` 就失败了，命令根本没发到板子。客户退回第 4 步点「刷新」，下拉里出现了一个
**新端口**，重选后写入正常。

**根因**：macOS 的串口名是 `usbmodem` + **USB 描述符里的序列号** + 接口号。同一块板
在不同固件/模式下序列号会变：

| 来源 | 序列号 | 设备名 |
|---|---|---|
| 客户当时那一路 | `123456`（Espressif 占位串号） | `/dev/cu.usbmodem1234561` |
| 刷完固件/应用起来后（本机实测） | `84C7BB70AF64`（MAC 派生） | `/dev/cu.usbmodem84C7BB70AF641` |

名字一变，旧路径就不存在了。而向导**打开时只枚举一次**端口（`Onboarding.__init__`），
第 5 步直接拿 `var_port` 里的旧名字去 `serial.Serial(...)`，于是报 ENOENT。
刷固件、板子从下载模式重启进应用、换 USB 口、Hub 掉一下，都会触发。

自证：`ioreg -p IOUSB -w0 -l | grep -i "USB Serial Number"` 看板子的串号，
再和 `ls /dev/cu.*` 对一下，名字必然是这个串号 + 接口号。

**修法（0.9.64）**：

- `provision.resolve_port(port)`：写入前重新枚举 —— 旧端口还在就用；只剩一个候选就自动
  改用并**明确提示**「端口已变化（A → B）」；多候选**不猜**，报错列出候选让人回第 4 步选；
  一个都没有就给「插好数据线/换 USB 口/点刷新」的人话；
- `provision._open()` 把 `FileNotFoundError` / `SerialException` 转成 `PortError`，
  带上当前候选列表 —— 不再把 Python 原始异常甩到界面上（原来那个红字就是这么来的）；
- 向导进第 5 步时刷新一次端口列表，写入前再复核一次；Wi-Fi 对话框（网络 → Wi-Fi/服务器配置）
  同样走 `resolve_port`；
- 单测：`app/tests/test_provision_port.py`（8 条：改名自动切换 / 多候选不猜 / 无候选话术 /
  `_open` 转人话）。

**客服话术（30 秒）**：

1. 先看终端 `ls /dev/cu.*` 有没有 `usbmodem…`；没有就是板子没连上，不是 Wi-Fi 问题；
2. 回到第 4 步点「刷新」，选**新出现**的那个端口，再写；
3. 换一根能传数据的线、直插 Mac 的 USB 口（别过 Hub）；
4. 端口反复出现又消失 = 板子在反复重启，先查供电/固件；
5. 确认没有别的程序占着串口（Arduino 串口监视器、esptool）。

### 2.30 校准卡在最小档位：小位移读不到 ≠ 指针丢了（2026-10-28 客户日志）

**现象**：校准反复在这一处断：

```
测量 BL x=20 · 约剩 6 分钟
BL x=20 读不到，跳过这一档
探针连续读不到，先退回帧差；读到就自动恢复
测量 BL x=40 · 约剩 10 分钟
中断：探针（Pointer Tester）读不到指针
```

客户连点 8 次「继续校准」，每次都在 x=40 中断。同一份日志里还有
`投屏延迟 2813 ms / 回执 1270 ms`（正常是 150–300 / 几十毫秒）。

**根因（两件叠加）**：

1. **链路太慢**：每档要等 2.89 s，而抓到的帧还是 2.8 s 前的 —— 指针在飞、被隐藏、
   或 HUD/二维码是旧的，探针和帧差都读不到；
2. **旧规则太急**：`x=20` 跳过之后，`x=40` 再失败就 `misses>=2` 判整轴废掉。而
   20 单位 ≈ 13 px，本来就在帧差噪声（10–40 px）里，高延迟下几乎必然失败 ——
   于是每一轮都死在同一格，续校永远推进不了。

**修法（0.9.64）**：`MissTracker` —— 小档位（<150 单位）最多连着跳 4 档，**不判废**；
中/大档位连续 2 次读不到才放弃这一轴；读到一次就清零。中断文案也改成
「指针读不到（探针和帧差都没读到）」，不再让用户去折腾一个已经失效的探针。

**先看哪个数**：`命令回执`。>300 ms 就先修 Wi-Fi（靠近 AP / 换 2.4G 信道 / Mac 插网线 /
停掉同步下载），**回执 1.2 s 时校准没有意义**，改算法也救不回来。投屏延迟 2.8 s 只是第二条证据。

## 3. 坐标与点击

- **布局会漂移**：信息 App 新建按钮实测 `y 0.885 → 0.935`；每次按最新截图取坐标。
- **`changed=true` 不代表成功**：hover 只有约 90 px；真实界面变化通常 > 1000 px。用 `min_change_px`（`click_text` 默认 500）。
- **顶部 6% 是 `Device.changed()` 的盲区**（避状态栏时钟）：TL/TR 停车点在 y≈3%，校准里不能用它判变化，要用 `_diff_pixels`。
- **边缘够不到**：BR/TL 停车点离边约 3–10%，`x>0.96` 的按钮可能点不到；必要时换角或截图确认。
- **底部 6% 精度下降**（`y>0.94`）：点控件上沿，或用键盘。
- **圆角不可达带**：iOS 把指针中心夹在圆角内，`x<0.15 且 y>0.97` 一带物理点不到；重试无意义。
  现在有几何模型：`control/corners.py` + 实测档案 `control/corner_profiles.json`
  （`源:宽x高` → inset / 半径 R），`click` 会返回 `predicted` 落点供对照；
  换手机/分辨率先用 `python control/measure_corners.py --device "…"` 量一份。见 §6.2。
- **点击默认 aim=True**：会先找指针纠偏，多花 1–2 s；返回里的 `pointer_err` 可判断这次准不准。
  `pointer_err` 突然从个位数变成 ~110 px 说明校准表已经不对（2026-10-22 遇到过一次），别硬补偏移，重校。
- **右键（`click 2`，固件 0.6.1+）是应用相关的**：备忘录列表能弹菜单，部分第三方列表不响应。
  换原生文本/列表界面验证，别拿单个 App 判断固件好坏。
- **MCP 已暴露右键（2026-10-23 实测）**：`click(x, y, button="right")` → 固件 `click 2`。
  实测 N16R8 + iPhone 备忘录列表弹出「共享 / 移动 / 删除 / 置顶 / 锁定 / 复制」（`changed_px=14753`）。
  注意：**工具 schema 要宿主重启 MCP 进程才会出现 `button`**（`control/mcp_server.py` 0.3.1）。
- **关闭上下文菜单别点看起来“空白”的地方**：iOS 的菜单项是**整格命中**，不是点文字才生效。
  2026-10-23 复核：右键备忘录列表第一条 → 菜单顶部一行三格「共享 / 移动 / 删除」（删除在**右上格**），
  OCR 中心 `删除=(0.834, 0.406)`，面板右缘到 `x≈0.95`；当年误点的 `(0.88, 0.42)`
  虽然看起来像面板右上的空白，却正好落在**删除格**里（该格约 `x 0.73–0.95, y 0.36–0.47`），
  所以当场删掉一条备忘录是真的（已按 §5 的“文件夹移动法”恢复）。
  关闭菜单用 **`esc`**（本轮实测可关）或点**远离面板**的空白（如最下方 `y>0.85`）；
  **不要点面板内部/边缘的任何“空白”**。
- **aim 会误判，别迷信 `pointer_err≈0`**：底部区域实测实际落点比目标低约 30 px，
  但 `pointer_err` 只有 1.0 px——它把界面里的灰色圆/阴影当成了指针。
  `y>0.9`、小图标、或同一目标连续 `changed=false` 时，把目标**上移 0.02–0.03** 再点，并重新截图核对。
- **滚轮其实能用（2026-10-22 实测，iPhone iOS 18 / 内嵌网页文章）**：`scroll N 0` 会让页面动，
  但**每份报告只走约 4–8 px**（图像对齐实测：5 次 ≈ 42 px），且 **N 的大小被忽略**
  （-1 / -5 / -20 位移一样），连发才累加。好处是**没有惯性**，发完停 0.25 s 就能截图。
  所以：整屏翻页仍用分段拖拽（`dy`）；微调走 `scroll(fine=N)`。旧文档「iOS 不认滚轮」是错的。
- **滚轮方向与 `dy` 相反（已修）**：固件 `scroll +N` 实际是「页面向下」——设置列表和内嵌网页列表
  都验证过（2026-10-22 复测）。工具层已把 `scroll(fine=…)` 取反，**与 `dy` 统一为「正数 = 更早/向上」**。
  个别表面（视频、部分 WebView）若方向相反，用 **设置 → 交互 → 滚轮方向** 翻转，别改代码。
- **滚轮跟着指针走**：iOS 只滚「指针下方」的滚动视图。指针停在底部工具栏/空白处时，滚轮一份报告都不生效
  （实测 `moved_px=0`）；`scroll(fine=...)` 会先把指针停到屏幕中央再滚。自己发 `scroll` 命令时别忘了这步。
- **拖拽/滚动松手前必须停住**：抬手那一刻 iOS 会按最近的速度结算惯性，边走边松会被当成甩动，
  页面再滑一段，截图和坐标就全偏了。`drag`/`scroll` 现在松手前停 `SETTLE_PAUSE`（**1.30 s**），
  并且 `drag` 先快后慢（ease-out）、末尾三小步减速（0.55 s 实测仍会被判成甩动），
  松手后先放 0.8 s，再按**像素差**连续 2 次无位移才截图（`_settle_shot`，最多约 3 s）。
  别用字节比对——同一画面重编码后 JPEG 字节也不同，会一直等不到「相等」；自己写脚本时别省这两步。

## 4. 校准

- 校准前先测**投屏延迟**（实测中位 223–355 ms），等待时间不短于「延迟 + 80 ms」。
- 网格测试页（静态、高对比、无 hover）是最好的校准画布。
- 校准表只有一个权威文件：`~/Library/Application Support/HIDBridge/calib.json`；
  GUI、MCP、CLI 都读它（`HIDBRIDGE_CALIB` 可覆盖），仓库里的只是种子。
- 动作前会自动按 mtime reload；`calibration_status.stale=true` 说明文件比内存新，调 `calibration_reload`。
- 校准完成后不需要重启 MCP（会自动 reload），但用 `calibration_status` 确认 `measured_at` 已变。
  **实测（2026-10-22）**：向导写完文件后 MCP 里仍是旧表（`stale=true`、`measured_at` 还是上一次），
  调一次 `calibration_reload` 才生效；这次校准 latency 206 ms、点击 `pointer_err` 6–33 px。
- `status.calibrated` 以控制层 `calib.json` 的 `corners` 为准；legacy 的 `server_calibrated` 另算。
- **校准失败/取消不再作废（0.9.44 起）**：每测完一个角（连停车点）就写
  `calib.wip.json`，向导给「继续校准（从 TR 开始）」，最坏只丢当前一个角（约 5 分钟）。
  正式表仍然是四角齐了才写；临时档案不参与点击计算。想从零重来就点「开始校准」。
- **`calib.json` 的 mtime 变了不等于表变了**：App 启动/切换档案时的「匹配校准」
  （profile probe，见 §0.0.3-6 的第二个写者）会**重写** `calib.json`——mtime 更新、
  内容里的 `measured_at` / `refs` 原样。2026-10-25 22:39 就差点把它当成"表被重写"。
  判断表有没有换，看 `measured_at` 和 `refs`，别只看 mtime；必要时 `calibration_reload`。
- **失败文案按四类给下一步**（探针 / 画布（锁屏、切 App）/ 链路 / 精度闸门），
  原始异常只进日志。用户不该再看到 `progress() missing 1 required positional argument`。
- **校准到底要多久（2026-10-25 22:00 真机实测）**：每档 **~17 s**（`settle` 轮询 + 探针读数，
  不是固定 sleep）。X 12 档 + Y 7 档 = 19 档/角 → **≈5.4 分钟/角**，四角 + 延迟 + 验证
  **≈24 分钟**。向导文案 0.9.44 起改为「15–30 分钟（视设备）」（原来写 13 分钟，偏乐观一倍）。
  续校时同样按「5 分钟/角」估：剩两个角 ≈ 10 分钟。
- **顶角上行距离的起点是占位值 400**，不是几何值：`tune_top_park()` 会在测顶角停车点之前
  按真值把它调到 3%–12%（实测 400 → 1093.5 / 1090.7）。所以临时档案里的 `park_up: 400`
  可以放心沿用——**别**把它换成 `0.94×屏高` 的估算当起点，那可能一上来就把指针顶到 y=0。

### 4.6 从 GitHub 下安装包：download 直链废、API 直链慢（2026-10-25 实测）

- `https://github.com/<owner>/<repo>/releases/download/<tag>/<file>`：**直接超时**
  （15 s 连不上，DNS/IP 层被掐）。别把 `browser_download_url` 当下载地址。
- `https://api.github.com/repos/<owner>/<repo>/releases/assets/<asset_id>`
  （带 `Accept: application/octet-stream`）：能下，但同一条链路**实测 ~40 KB/s**
  （curl 24 s 只拿到 1 MB），97 MB 的 DMG 要 ~40 分钟。
- **结论（用户 23:57 定）**：MCP **不在本地下载/安装**，只把
  `https://github.com/jianghui1974/Quileg-HID/releases/latest` 交给用户去点。
  97 MB 在 40 KB/s 上要 40 分钟，还要配续传/token/验签/回滚——收益远小于风险。
- 曾经实现过的下载/安装（`bd4df7f`）已删除；需要时从 git 取回。
- 如果将来真要做下载：Release JSON 的 `assets[].id` 就是 API 直链要的 id；
  `assets_url` 形如 `…/repos/<o>/<r>/releases/<id>/assets`，切掉 `/releases/` 得到 repo 根；
  校验只能靠发布页那份 `<name>.sha256`（94 B，同样走 API 直链取）。

### 4.4a 打包偶发失败：`codesign` 报 "A timestamp was expected but was not found"

2026-10-26 23:20 的 arm64 构建挂在 3/6 步：

```
.../Contents/Frameworks/airplay/gstreamer-1__dot__0/libgstapp.dylib: A timestamp was expected but was not found.
```

不是代码问题：`--timestamp` 要向 Apple 的时间戳服务器申请，**那一次请求失败了**，嵌套组件的
签名因此没有时间戳。同一份代码**重跑一次就通过**（23:29 `status: Accepted`）。

处理顺序：① 先原样重试一次；② 还不行就单独验服务器——
`codesign --force --options runtime --timestamp --sign "<ID>" /tmp/x.dylib`，成功说明服务器没问题，
那就是优先级/嵌套顺序的事（可改成先逐个签 dylib 再 `--deep` 签整个 app）。

**顺带一个坑**：`build_release.sh 2>&1 | tee log` 的退出码是 `tee` 的，构建失败也会显示成功。
判断成败要 `grep "status: Accepted"`，或者看 DMG/`stapler` 有没有产出。

### 4.4b `github.com:443` 不通时怎么发版（2026-10-27 实测）

同一台机器上：`curl https://github.com` 超时（75 s 连不上），`https://api.github.com` 正常。
于是 `git push` 全挂，但 `gh release create/upload` 照常成功 —— **gh 走 API，git 走 443 直连**。

- 发版（上传资产、建 Release）不受影响：`gh release create …` 直接可用；
- **改仓库文件**（README、`docs-src/VERSION.txt`）改用 Contents API 提交：

```bash
sha=$(gh api repos/<o>/<r>/contents/README.md --jq .sha)
b64=$(base64 -i README.md | tr -d '\n')
gh api -X PUT repos/<o>/<r>/contents/README.md \
  -f message="docs: …" -f content="$b64" -f sha="$sha" -f branch=main
```

- 提交后 GitHub Pages 会自动重建（`gh api repos/<o>/<r>/pages/builds/latest` 看 `status`）；
- 校验文件是不是真的更新了：`gh api .../contents/<path> --jq .content | base64 -d`
  （别用 raw.githubusercontent.com，同样可能被掐）。

### 4.4c `notarytool` 卡在 "Conducting pre-submission checks" 不报错（2026-10-27 实测）

**现象**：`xcrun notarytool submit <dmg> --wait` 卡在 pre-submission checks 十几分钟，
`notarytool history` 里**查不到这次提交**（说明连提交都没建起来）。Network 到
`appstoreconnect.apple.com` 正常，keychain 也解锁着。

**根因**：**DMG 还挂在系统里**（之前 `hdiutil attach` 验证包子时留下的挂载，`/Volumes` 里看不到
也可能仍在：`hdiutil info -plist` 里还列着 image-path + diskimages-helper）。

**处理**：

```bash
# 找到那个镜像的设备号（不要用 /Volumes 猜）
hdiutil info -plist | plutil -convert json -o - - | python3 -c "...images→system-entities..."
hdiutil detach /dev/diskNN -force
```

## 4.5 UVC 采集卡（HDMI 有线投屏）

| 现象 | 根因 | 规避 |
|---|---|---|
| 整屏绿色雪花、画面隐约可见 | 采集卡发 **UYVY（`2vuy`）**，AVFoundation 的 BGRA/NV12 转换在这块 Hagibis(MACROSILICON) 上是错的 | 取原生 `2vuy`，自己按 UYVY 解释；ffmpeg 用 `-pixel_format uyvy422` |
| 找黑边全失败，整帧都被当成画面 | `2vuy` 是 **Cb Y Cr Y**，亮度 Y 在**奇数字节** | 扫描 `p[y*bpr + x*2 + 1]`，不要读第一个字节 |
| OCR 在 888×1920 上反而更差 | Apple Vision 对大字号不敏感 | 送 OCR 前缩到 ~600 宽；坐标仍归一化 |
| 画面横过来了 | 采集卡的「竖屏模式」把竖屏内容旋转 90° 塞进 1920×1080 | **不要只靠宽高比**（真横屏 App 也是 2.17）。按「文字行横竖 + 时钟在不在上半屏」判定：`uvc-frame --rotate ocr` 自动转，`orientation()` 可复核 |
| OCR 四个方向都能读出字 | Apple Vision 对旋转文字有一定识别力 | 用 bbox 的宽>高 判横排、`HH:MM` 的 y<0.5 判正立，别用「文字总量」当方向分 |
| 第一帧有撕裂/上半屏噪声 | 刚 startRunning 时的半帧 | 丢掉前 2 帧再发 |
| 拔掉采集卡后画面变成「摄像头看到的房间」 | 旧逻辑取「第一个外部摄像头」兜底，iPhone 连续互通相机也是 external，被当成了采集卡 | 只认 `modelID` 含 `uvc` 的外部设备，并排除 FaceTime / iPhone / iPad；找不到就报错退出，不申请权限、不回退摄像头 |
| 同一个 `key` 在 Windows 上行为不对 | `cmd` 在 Windows 是 Win 键；策略按平台区分 | 统一写 `gui`，先 `keymap_check(platform="windows")`，别用 iOS 经验套 |
| F1–F12/Home/End 发不出去 | 固件 < 0.6.0 没有这些键 | 升级到 0.6.0（本机已升级）；老固件会返回 `firmware_unsupported`，不要重试 |
| 换视频源后点击整体偏 | 不同源的画面尺寸/裁切不同，旧档案是按分辨率存的 | 档案键改为 `源:分辨率`（`airplay:500x1080`、`uvc:888x1920`），切源时按 `X-Video-Source` 自动启用；没有对应档案就不会乱用别的源 |
| 双开时只有一路有实时画面 | **iOS 同一时间只维护一个外接显示/镜像会话**：接了 HDMI 再开 AirPlay 镜像，另一路会停在最后一帧（或反之）。`live` 只代表 UVC 有 TCP 连接，不代表有帧 | 所以**不做自动切换**：手动选源，另一路只做监视。界面按内容变化标「实时 / 无更新 Ns」，冻结的格子边框变琥珀色。 |
| 采集卡插着但 HDMI 没接，AI 仍把它当画面 | 采集卡会输出纯色/「无信号」底图，`live` 仍为 true | 缩略图灰度标准差 < 6 连续 3 秒 → `signal=false` 并提示；**不会自动换源**（需用户手动切） |
| 拔卡后插回不恢复 | 旧 helper 进程不退出，AVCaptureSession 跟着设备一起死了 | 看门狗：5 秒无帧且 `isConnected=false` → 退出码 3；服务端每 10 秒重试，插回后自动重建（实测 **10 秒**恢复） |
| 日志里出现两套 `AirPlay receiver started` / `UVC capture started` | GUI 刚启动、`:8890` 还没监听时，MCP 宿主拉起 `--mcp`，旧逻辑会自己再起一套服务端 | 0.9.4 起用 `server.lock` + 先等 2 秒；抢不到锁就等对方的 API |
| App 请求相机**不弹窗**、直接拒绝 | hardened runtime 的 App 缺 `com.apple.security.device.camera` 权限，TCC 的规则是「缺少权限就不弹窗」 | entitlements.plist 加 camera；Info.plist 加 `NSCameraUsageDescription`，两者缺一不可 |

> 实测日志（2026-10-21）：
> `service: kTCCServiceCamera requires entitlement com.apple.security.device.camera but it is missing … Policy disallows prompt … access denied`

## 5. 数据安全（真实踩过）

- **误删备忘录**：`文件夹 → 最近删除 → 编辑 → 选中 → 文件夹图标 → 备忘录` 可恢复（30 天内）。

## 9. 便宜板（ESP32-S3-N16R8）：XMC Flash 的坑（2026-10-22 实测）

> 背景：XIAO ESP32S3 Plus 较贵，改用 YD ESP32-S3-COREBOARD V1.4（N16R8，¥20 级）做实验。
> 固件改用统一的 `s3_16m_universal`（见 `firmware/hid_bridge/src/board.h`）。

### 9.1 烧官方 16M 镜像后无限重启

- **现象**：串口每 ~0.3 s 刷一次 `E bootloader_flash: XMC flash startup fail` /
  `failed when running XMC startup flow, reboot!`，BLE 名不广播，App 看不到板子。
- **根因**：IDF 5.4+ 的 `bootloader_flash_xmc_startup()` 用白名单判 XMC（MFID `0x40/0x41/0x50`）；
  这颗 **XM25QH128A 是 MFID `0x70` / CPID `0x18`**，不在名单里 → 被强制跑一轮复位序列 →
  跑完仍认不出 → 重启。原厂固件（老 IDF，无此逻辑）能启动，可用来排除硬件问题。
  Espressif 官方表态不修（[esp-idf#18947](https://github.com/espressif/esp-idf/issues/18947)）。
- **规避**：`firmware/tools/patch_xmc_bootloader.py`（`build.sh` 的 16M profile 自动调用）
  把该函数改成"立即返回 OK"（等价老 IDF 行为），并按 esptool 规则重算 checksum + SHA256。
  对非 XMC/白名单内的芯片是恒等变换。
- **判断命令**：`esptool flash-id` 看到 `Manufacturer: 20 / Device: 7018` 即可确认。

### 9.2 用 App 刷机会报串口噪声

- **现象**：`Invalid head of packet (0x81/0x30): Possible serial noise`。
- **根因**：这块板的 CH343 链路在 460800/921600 下不稳。
- **规避**：刷机用 **230400**（`app/core/firmware.py` 已改默认值；115200 也稳）。

### 9.3 NVS 配置写不进去（**已解决**，2026-10-23）

- **现象**：串口 `cfg<...>` 回 `ok saved`、`cfg?` 当场能读回，但**重启后配置丢失**，
  Wi-Fi 不会自动连。表现为"配了网，一断电就没了"。
- **根因**：**Flash 模式不匹配**。Arduino-ESP32 核心默认按 **QIO** 编译；这颗 XMC 的
  状态寄存器写不进去（启动日志 `Failed to set QIE bit, not enabling QIO mode`），
  bootloader 把 MMU 回退到 DIO，但运行期 `esp_flash_read` 仍按 QIO 发读命令 →
  **读数据分区一律返回 `0xFF`**。写是好的，所以"写成功、读不到"——NVS 的 CRC 校验失败，
  键等于不存在。
- **判定方法**：在固件里 `esp_partition_write` 64 字节后立刻 `esp_partition_read`，
  比较是否一致（`match=0` + `back=ffffffffffffffff` 即是本问题）；
  同一地址用 esptool 读却是对的 → 证明"写没问题，固件读路径坏了"。
- **规避**：16M 通用镜像**显式用 `FlashMode=dio` 编译**（`firmware/build.sh` 已固定）。
  注意：只给 esptool 加 `--flash-mode dio` 改镜像头**不够**，必须重编译 bootloader。
- **验证**：`flashprobe` → `match=1`；`probe` → 同句柄/重开句柄都能读回；
  `cfg` 写 → 重启 → `cfg?` 仍在。
- **顺带修掉**：`ConfigStore::save()` 原先不检查 `put*` 返回值，写失败也回 `ok saved`
  （App 会显示"已保存"）。现在写后回读校验，失败返回 `err nvs write used=.. free=..`。
