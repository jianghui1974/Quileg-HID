## 0. 开工 30 秒检查

```text
status()      → device / screen / positioning（table 还是 visual）
screenshot()  → 当前页、列、键盘状态、是否有弹窗
```

- `screen=false`：等 2 s 再看一次；仍 false 就请人重开「屏幕镜像」，不要反复重试。
- `positioning=visual`（没有表）：也能点，但每动作多 2–6 s、误差 10–40 px；**不必强制校准**（§2.21）。
- **截图可能晚一帧**：每个动作后多截一张再判断，否则会把「已提交」看成「还在输入」。
- 主屏有**多页、每页列数不同**：同一坐标在不同页可能是不同 App，先看截图再点。

> **iPhone 端三个总开关（每次新设备/换机必查，埋得很深）**
>
> 1. **辅助触控必须开**：`设置 → 辅助功能 → 触控 → 辅助触控`。不开就没有鼠标指针，
>    所有 click/move 都像"没反应"。
> 2. **鼠标键「使用主键盘」必须关**：`… → 指针设备 → 鼠标键 → 使用主键盘`。开着时键盘被当成鼠标：
>    `i j k l m o u 7 8 9 .` 不落屏、回车不换行而是弹菜单、指针乱跳。**2026-10-22「11 个字符永不落屏」
>    的真正原因**，关掉立即恢复，不用重启手机。
> 3. **自动锁定必须设「永不」**：`设置 → 显示与亮度 → 自动锁定`（iPhone / iPad 同）。锁屏会让投屏停住；
>    校准跑到一半锁屏就是整轮作废。这是唯一一个「不设也能开始、跑到一半才炸」的开关，装完就该提醒用户。

> **反模式：别自己发明流程**
>
> - ❌ 手改 `calib.json` / 自己补像素偏移 / "这次先 +0.02 试试"——校准错了就 `calibration_request`；
> - ❌ 不用 `click_text` 而靠目测坐标反复盲点；不用 `scroll(fine)` 而自己拼拖拽；
> - ❌ 连续 `changed=false` 不换目标、不查日志，闭眼重试；
> - ❌ 绕过 MCP 直接 `curl /api/raw` 或写脚本操作手机（排障例外，要说明）；
> - ❌ 自己跑校准向导（必须用户点「开始」）；
> - ❌ 遇到问题先怀疑固件/重装 App，而不是先看 `status` / `app_logs`。
>
> **先翻 AI_GUIDE §1.0 的工具表，再动手。**

### 0.1 新设备 / 新场景：先建立基线

**同一套坐标、滚动距离、返回手势不要跨设备复用。** 第一次接触一台设备或一个 App，先记下：

| 项 | 怎么取 |
|---|---|
| 设备 / 系统 | 用户告知，或从屏幕「关于本机」看 |
| 指针大小 | 设置 → 辅助功能 → 触控 → 辅助触控 → 指针控制 |
| 镜像分辨率 | `status()` 的 `aspect`、截图尺寸 |
| 校准 | `positioning` + `calibration_status` 的 `table` |
| 投屏延迟 | 校准向导第一步会测（正常 0.2–0.53 s） |
| BLE | `status` 里 `connected/encrypted/sub/kb/ms` |

然后用计算器 `7+8=15` 验证这张表是否适合当前设备。基线记进 §6.1。

## 1. 屏幕源（AirPlay）

| 现象 | 根因 | 规避 |
|---|---|---|
| App 打开后画面变横屏、随后**冻结**，点击/滚动帧 hash 不变 | 部分第三方 App 的投屏保护 | 换 App；或用 UVC 绕过；**不要重校准**（不是坐标问题） |
| 使用上述 App 期间 `screen=false`，UxPlay 被看门狗重启 | 投屏会话被 App 带崩 | 等 / 请人重投屏；不要连续操作 |
| 同局域网多台 Mac 的投屏名都叫 `Quileg` | 接收端名写死 | 现为 `Quileg - <电脑名> (4位ID)`；BLE 名本身带 MAC 后缀 |
| 画面静止时取不到新帧 | AirPlay 只在画面变化时发帧 | 用「画面变化」判断，不要用「帧新鲜度」 |

> 实测记录见 §1（archive）。

## 2. 输入、探针与校准（40 条，按「现在还要不要管」重排）

### 仍然要遵守

**§2.1 键盘被当成鼠标** —— 三个症状一起出现就是它：部分字母不落屏、回车弹菜单、指针乱跳。
`设置 → 辅助触控 → 指针设备 → 鼠标键 → 使用主键盘`**必须关**。（详见 §2.1）

**§2.2 语音桥：Mac 朗读 → 手机听写**（中文输入最快的路）

- 前提：手机 `设置 → 通用 → 键盘 → 听写 → 听写快捷键 = Control`；
- 起停：`dictation("start")` / `dictation("stop")`（内部先按 Shift 唤醒，再双击/单击 Control——
  **iOS 会吞掉空闲后的第一次按键**，直接连按两次 `ctrl` 常常只算一次）；
- 转写延迟 1.5–3 s（验收等 2–3 s）；暂停态仍收音；Spotlight 不吃听写；30 s 静音自动结束。
（详见 §2.2）

**§2.4 iPad「锁屏」其实是顶边面板** —— 被控设备是 iPad 时，指针碰到屏幕顶边（y≈0）会拉下
通知中心（左半）/ 控制中心（右半），全屏毛玻璃看起来和锁屏一样。`esc` 可关。
所以 iPad 的顶角停车点不在 0，而是从底边上行 `park_up` 到达。（详见 §2.4）

**§2.6 / §2.7 刷机：分区表与容量** —— 「仅升级固件」只写 `app0`，分区表原样保留。板子如果残留
别的分区布局（或只有 8 MB flash），刷写会报成功，但**Wi-Fi 配置永远写不进去**。
现在 App 会先 `esptool flash-id` 比对，不符就拒绝；改分区表只能整包刷。（详见 §2.6 / §2.7）

**§2.21 校准是「可选加速器」，不是门槛** —— 没表也能干活（`positioning=visual`），
所以**不要**因为 `calibrated=false` 就停下、也**不要**劝用户为了几 px 反复重校。
设备是无限的，表只能是一个不断更新的缓存。（详见 §2.21）

**§2.22 `ACK ≠ 送达`** —— `move` 返回 `{"ok":true}` 只代表报告进了 BLE 缓冲，不代表手机收到。
链路抖一下，指针没动、工具链看到的是成功，于是这个点偏几百 px。这种失败**没有异常可捕**，
只能靠重试兜住。现有四层：命令级重试 → 单点重测（偏 >250 px）→ 整轮重验 → 断点续校。
（详见 §2.22）

**§2.23 网页版探针的两条死区** —— 独立窗口的视口比屏幕矮约 50 pt，且**屏幕底部约 6%（y>0.938）
收不到 hover**；状态栏那条也收不到。所以：**iPhone 整表校准必须用原生 App**，
iPad 可以用网页版，日常读数两台都行。页面自己也会写「校准请用原生 App」。（详见 §2.23）
**2026-10-30 起 probe-web v6 补齐了 ⌘I / ⌘K / ⌘B** —— 以前网页版完全不认键，
宿主一切粗测就是「发出去、没反应、读回还是 fine」，粗测直接作废。

**§2.26 动作后的截图会晚一整步** —— AirPlay 只在画面变化时发帧，动作刚发完拿到的还是旧帧。
`click`/`key` 现在的口径是「等一帧比动作前**新**的 → 等转场 → 用稳定帧算」，返回里有
`changed / changed_px / fresh / frame_age_ms`。**`changed=false` 也不等于没生效**（同一小节 §2.26a），
真正要判「有没有生效」时看 `changed_px` 的量级（真实界面变化 >1000 px，hover 只有约 90 px）。
（详见 §2.26 / §2.26a）

**§2.27 程序坞是我们自己扫出来的** —— 底部锚定会碰屏幕底边，程序坞随即弹出并盖住最下面约 18%，
所以 `y>0.75` 的目标要「先到中部等 0.9 s 再下潜」。`dock_visible` 只报「动过」，不猜开关。
（详见 §2.27）

**§2.28 OCR 降级成 `.fast`** —— 不是签名问题，是 ANE / mach-lookup 被掐。0.9.63 起结果里带
`degraded` / `degraded_reason`，MCP 与 GUI 都会说出来。看到 `degraded=true` 就别再追「为什么字变少了」。
Intel 包因 Vision 限制**本来就常走 `.fast`**（§2.3），这是设计而非故障。（详见 §2.28 / §2.3）

**§2.29 串口改名** —— 写 Wi-Fi 报 `[Errno 2] could not open port …` 多半是板子换了 `/dev/cu.usbmodem*`
名字（0.9.64 起会自动 `resolve_port`）。仍失败时 `ls /dev/cu.usbmodem*` 人工确认。（详见 §2.29）

**§2.31 打包 Swift 小工具必须指定真实 `-target`** —— `build_release.sh` 已固定
`ocr`/`textsize` → `macos13.0`、`uvc` → `macos14.0`，并有 `nm -u | grep __StaticArrayStorage` 闸门。
**别「按宿主编译、事后改 minos」**：dyld 只认符号，改 plist 的 minos 没用，旧 macOS 上直接起不来。
（详见 §2.31）

**§2.39 校准的「增益」是设置给的，不是常数** —— iOS 指针设备的「初始延迟 / 最大速度 / 追踪灵敏度 /
滚动速度」直接决定「单位→像素」增益，而校准表就是对这条曲线采样。**设置一改，旧表立即作废。**

- **没有通用换算常数**：实测两台机器差 4 倍 —— 直角屏 608×1080 是 **0.547 px/单位**（一屏高≈1850 单位），
  圆角屏 500×1080 是 **1.32→0.68 px/单位**（≈450 单位）。**别再用「1100 单位 ≈ 一屏高」当判据**（已推翻）；
  要看就看表里测出来的 px/单位，或者 `calibration_status.y_reach`。
- 测增益的正确姿势：读数前先 `move 2 2` 挠动把 AGE 归零；基点落在探针 HUD 卡片下方；
  用 ±40 / ±80 小步来回 6 次取中位；
- **别** `home` + 大位移再读——会「闪过几个位置直接落进盲区」，HUD 停在旧值上，看起来像没变。
（详见 §2.39）

**§2.40 TL 角：不是「停车点贴顶」，是文字 HUD 盖住了它** —— TL 用「home → 对角压 25 单位」停在
`(0.0507, 0.0233)`；而原生探针 HUD 占 `y 0.09–0.64、x 0–0.92`，指针停进卡片后 hover 不再更新。
于是 TL 的 x 轴整段量不出来。**0.9.70 一度以为是停车点贴顶、准备去抬停车点 —— 方向错了。**

- **2026-10-29 定案（探针 0.2.5）**：HUD 默认不显示（⌘K 才调出来），盲区整个消失；
  TL 直接可测、**不再镜像**，停车点也从「几何模型估的 (0.0507,0.0233)」变成
  「探针真值测的 (0.1385,0.0649)」。验证中位 11.8 → 6.8 px、最大 103.8 → 19.9 px。
- **教训**：「某个角量不出来」时先问「那块屏幕区域**有没有东西盖着**」，再怀疑停车点/几何。
  探针自带的 UI 也是一种遮挡。
（详见 §2.40）

**§2.43 三条「不是故障」的现场规则**（2026-10-30，客户新手包实测总结）

- **能点不能滚**：iOS「执行触控手势」关着时，鼠标拖拽不模拟手指 —— `scroll`/`drag` 全废，
  而点击、输入、按键照常。判据：文本框能打字、按钮能点，就是列表滚不动。
  路径：设置 → 辅助功能 → 触控 → 辅助触控 → 指针设备 → **执行触控手势 = 开**。
  **别重装、别重校、别怀疑固件**（客户现场一开始就误判成「滚动坏了」）。
- **画面只剩 16:9 纯视频、0 个文字块**：某些 App 会把视频**独占**推给外接显示（播放类 App 的正式版实测；
  AirPlay 与 UVC 都一样），UI 根本不在镜像里。判据：同一时刻切到 Safari/主屏画面立刻正常。
  处置：换同系列的**轻量/极速版**（实测能正常 500×1080 全屏镜像），或改用列表/双列模式；
  **不要**在这条路上做代操作。
- **手机说「已复制」，Mac 的 `pbpaste` 没变**：Universal Clipboard 是**同一块**剪贴板，
  Mac 上刚复制过别的东西就会把手机送来的 URL 顶掉（实测三轮 `url=none`，面板/toast 都正常）。
  跑批期间 Mac 上不要复制粘贴；拿不到链接时**不要把浏览器地址栏 OCR 硬读**（字太小、错一个字符
  就是另一篇），贴在备忘录里用正文字号整行 OCR，再和标题/作者对一遍。

**§2.44 「BLE HID 触发不了 iOS 快捷指令」是错的**（2026-10-30 实测更正）
板子同时声明键盘+鼠标，一度以为 iOS 会把带修饰键的命令全交给 SpringBoard、快捷指令收不到。
实测：给快捷指令设了键盘快捷键后，`⌘1` / `⌘2` / `⌘3` 分别打开了 微信 / 备忘录 / 相册（0.9.77 + 固件 0.7.0）。
**用法**：让用户把每天重复的步骤串成一个快捷指令、设一个 `⌘+数字`，AI 发一次键就等于跑完一串动作；
**映射是用户自己设的**，第一次用之前确认一次（发一次看画面），别写死。
（同一条也解释了为什么"快捷键没反应"要先问"用户到底有没有设"。）

**§2.42 PyInstaller 会吞掉 datas 里的符号链接** —— 2026-10-30 出 0.9.77 Intel 包时踩到：
`airplay/gstreamer-1.0` 是指向 `gstreamer-1__dot__0` 的软链，x86_64 那份 PyInstaller 复制 datas
之后**插件目录在、软链没了**。后果很隐蔽：App 能启动、链路能起，但 `GST_PLUGIN_PATH`
指向一个不存在的目录 → GStreamer 一个插件都加载不到，画面解不出来。
`build_release.sh` 现在在打包后检查并补回这条软链（两个架构都兜）。
**判据**：`ls -la Contents/Frameworks/airplay | grep gstreamer` 必须看到 `gstreamer-1.0 -> gstreamer-1__dot__0`。

**§2.41 粗测（可视性扫描）四个把结论做反的坑** —— 2026-10-29 真机，全部踩过一遍。

- **先测延迟再扫**：不调 `measure_latency()` 时 `_settle` 退化到 0.2 s，帧还没更新就读，
  扫描出来一步一个 `B`。实测这台机器延迟 150–250 ms。
- **令牌要按「动没动」判，不能按「在不在」**：App 的 hover 超时/`.ended` 会让令牌消失，
  而那一刻指针可能就在看得见的地方 —— 「不在场」会给出**假盲区**。我们刚发过 `move`，
  令牌没跟着走才是真盲区。
- **一个令牌都没有时别靠白点判盲**：精细模式下二维码黑白边缘的 **JPEG 色度镶边**也是一片
  「高饱和像素」，会把整张画布当令牌，于是在错误的模式下也能一路报 `V`。现在 `_token_blob`
  同时卡包围盒（≤30% 屏宽）和填充率（≥35%），并且 `coarse_scan` 有**硬门禁**：不在粗测模式直接抛错。
- **HID 键盘空闲后第一个按键会被 iOS 吞**：`⌘I` 连发三次都不生效。发键前先敲一个无害的
  方向键当垫片。
- **服务层写 `gui`，固件只认 `cmd`** —— `key gui+i` 会被板子回 `409 err unknown key`，
  而且**看起来是成功的**：`set_probe_mode()` 在「已经在该模式」时会直接返回 True，
  所以 0.9.71 之前一次都没真把键发出去过，直到真机逐条试才发现。发键必须过
  `keymap.to_firmware()`（`gui` → `cmd`）。
- **命令偶发 409 Conflict 不算「切不过去」**：板子的 Wi-Fi/BLE 共存会让 `raw("key …")` 偶发
  409（MCP 同时在轮询 :8890 时尤其容易撞）。2026-10-29 `set_probe_mode` 就把一次 409 当成
  「探针没有粗测模式」，粗测静默跳过。`_is_link_error` 本来就把 409 列为「值得等」，
  发键必须走 `_retry`。
- **切回精细失败 = 整轮校准看起来像坏了**：断链会让 `_coarse_phase` 的 `finally` 切不回去，
  探针留在清屏状态，之后每一档都「读不到指针」。现在结尾多给几次机会 + 记
  `_probe_left_coarse`，`_calibrate` 开头 `_ensure_fine_mode()` 兜底。

（详见 §2.41 / HANDOVER §3.2）

**§2.42 校准档位表不能写死上限，表尾也不能剪「贴边档」** —— 2026-10-29 iPhone SE。

- **指针速度是用户设置**：`STOPS_Y` 原来到 1500、`STOPS_X` 到 1100，按 1.1–1.5 px/单位设计。
  SE 实测 1500 单位只走 0.77 屏高 → 表断在 77% → 闸门判「底部 23% 没有映射」（按钮会静默点空）
  → 整轮作废。现在走完固定档位后按 1.35× **续延**（≤6 档 / 6000 单位），直到贴边。
  （HANDOVER §3 那条「0.40 px/单位 → 一屏要 2700 单位」就是这个坑的早期记录。）
- **`clean_table` 的表尾规则会剪掉「跳到贴边」的那一档**：判据是「末尾这步 > 4×中位步长」，
  而 `600→0.77`、`750→0.999` 一步跳 0.22，正好超阈值 —— 剪掉之后覆盖率掉到 77%。
  现在贴边值（`≥0.98` / `≤0.02`）**永远不剪**。
- **直角屏 vs 圆角屏**：圆角屏上指针推到角会沿弧滑开，停车点被顶回 0.19；直角屏直接到
  `0.011 / 0.999`。所以 `corner_profiles.json` 的圆角模型对 SE **没有条目也不影响**（探针读得到真值）。

**§2.43 评估校准表的三条硬规矩（2026-10-29 一晚踩出来的）** —— 谁违反谁得出错结论。

- **单次 16 点随机验证不能用来比较两张表**：方差大到能把**打平**的两张表显示成
  `6.8 / 19.9` vs `25.1 / 88.1`。当晚据此连跑两次 20 分钟重校、还错误归因到 refs 上。
  正确做法：**同一批固定点 + 交替配对（A/B/A/B）+ 算配对差**。
- **两边的「起点」必须一致**：`units_for()` 得到的位移，只有在**与建表时相同的起点**
  出发才有意义。拿它从另一个锚点起步，会凭空多出 ≈0.17 屏宽（≈85 px）的系统偏差，
  而这个偏差会被误读成「表不准」。
- **6×6 的粗网格 + 双线性插值不够**：实测单元内误差 3.4–57.9 px。要用至少 9×13，
  或者非均匀网格（中间稀、边角密）。

**§2.44 探针「看起来全屏」不等于全屏** —— `prefersStatusBarHidden = true` 写在被
`present` 的控制器上是**不生效的**，必须加 `modalPresentationCapturesStatusBarAppearance = true`。
2026-10-29 之前一直没生效（时间/电池都盖在画布上），而**顶部那条 hover 盲区就是状态栏区域**：
隐藏后指针到 12 pt（1.8%）仍可读，圆角 iPhone 的 TL 停车点从 `(0.139, 0.065)` 收到
`(0.034, 0.016)`，TL 不再需要镜像。教训：**「某片区域读不到」先问「那里有什么东西盖着」**，
探针自己的 UI 也算遮挡。

**§2.45 「验证通过」≠「读数是真值量的」**（2026-10-31，新增条目，archive 里没有对照）—— `validate()` 和 `band_check()`
在探针读不到时也会回落帧差，所以**没有探针的表照样能 0.75 px 通过验证**，而落点实际
差一档（圆角机 6 px 中位那类）。以前这件事完全不可见：`positioning=table` +
`calibrated=true`，界面写着「定位 表」，用户只觉得「点得有点歪」。
现在看两处：`status.measurement.source`（本次读数走 probe 还是 frame）和
`calibration_status.measure.source`（这张表是 `probe` / `mixed` / `frame` / `model`）。
**别把这类误差算到表形状上** —— 形状没问题，读数源有问题；解法是开探针重校，
不是改档位（§3.4 已三次否掉）。

**§2.46 AirPlay 镜像流全程只有一个关键帧**（2026-10-31，新增条目）—— 抓 682 KB 原始码流统计 1 599 个 NAL：`{type1:1596, type7:1, type8:1, type5:1}`，SPS/PPS/IDR **全在会话最开头**，之后全是 P 帧，手机怎么滑都不会再出 IDR。

所以 **「中途开始录一个新 mp4」在协议层不成立**：
* `h264parse` 只拿到 SPS、拿不到 IDR 时会吐一个**没有 PTS** 的配置包，`mp4mux` 直接
  `Could not multiplex stream. Buffer has no PTS.` 并**整轮拒写**（文件 0 字节）；
* 源没声音时挂着的音频轨永远没数据，`mp4mux` 会等它 —— 同样一个字都不写。

正解：**镜像一连接就从会话起点录（环形），MCP 的「录制」= 按时间窗口导出**
（`ffmpeg -ss T -t D -c copy`，实测 5.02 s / 不转码）。详见 `docs/recording-design.md`。

**音频 pad 不能懒挂载**（2026-10-31 实测否定）：`mp4mux` 开流后 `request_pad_simple`
只会一路报 `QUILEG-RECORD: could not link audio pad`，文件照样 0 字节。
形状只能**开流前**定死，所以 UxPlay 侧改为「先缓存画面、3 s 内等到第一个节目音包就带音轨、
等不到就建纯视频 mux」（`decide_audio()`）。

**同一个坑的三条错误直觉**（本地 `gst-1.28.8` 用 `tools/rec_mux_probe.c` 复现，2026-10-31）：
* 「`appsrc is-live=false` 就不写 moof 分片」——**不成立**。非 live appsrc 照样写
  `moov` + 2 s 一档的 `moof`（分片和 is-live 无关）；
* 「先 PAUSED、第一帧到了再 PLAYING 会对齐 PTS」——**这才是 moov 不写的原因**：
  管道里有 live 源时 PAUSED 返回 `NO_PREROLL`，永远等不到 preroll，`mp4mux` 连
  `moov` 都不写（45 MB / `moov=-1` 就是这么来的）。**建管道就 PLAYING**；
* 「`is-live=true` 会把 PTS 落后的帧当迟到帧丢掉」——**不成立**：缓存 3 s 的 210 帧
  补推时一帧不少，mp4mux 照单全收。真正会卡住文件的是**没数据的音频 pad**（0 字节）。

**§2.47 分片模式选错，窗口导出只能导开头几秒**（2026-10-31，新增条目）——
`mp4mux fragment-mode=first-moov-then-finalise` 写出来的文件，**AVFoundation 裁不了**：
`clip --start 10` 报 `-11800 / -16364`，`--start 2` 却能过 —— 于是「录了 20 分钟，
只能导出前 8 秒」这种事故会安静地发生（ffmpeg 读同一文件完全正常，所以只看 ffprobe
发现不了）。根因是这种布局的 moov 只描述文件头部那一段，后面全是 moof，AVFoundation
不认这种混合结构。

**用 `fragment-mode=dash-or-mss`**：moov 在头、2 s 一档 moof，AVFoundation 从 0 到末尾
任意偏移都能裁（实测 start=2/8/12/26 全过）。代价：dash 模式收尾时**不写最终 moov**，
文件永远是分片形态（ffmpeg/AVFoundation 都能读，导出的 clip 是普通 mp4）。
`tools/rec_mux_probe.c` 是当初用来复现这些的本地装置，改录制参数前先在那里跑一遍。

**§2.48 iOS 截屏是 `⇧⌘3`，别按 Mac 的 `⌘⇧4`**（2026-10-31，实测）—— 接硬件键盘的
iPhone / iPad 上，`⇧⌘3` 就是系统截屏（截图进「照片」+ 左下角预览，实测出现预览条）；
`⇧⌘4` 在 iOS 上仍标为实验（没验过），`⌘⇧4` 是 Mac 的选区截屏，**别混**。
0.9.79 起 `shift+gui+3` 从实验提到白名单直接允许（`control/keymap_default.json`），
`key(action="screenshot")` 就是它；截图是**相册里的真文件**，所以能接用户自建的快捷指令
（截图 → 提取文本 / 翻译 / 存备忘录），**端侧 OCR 这条路成立**（说明见 AI_GUIDE §4.14；
映射和产物去向都是用户自己定的，别预设、也别替用户配）。两个注意：截图**留在用户相册**里
（别刷屏），`key()` 回执里的图是投屏画面，不是相册里那张。

### §2.40 `aim` 的纠偏会**静默失效**（2026-10-30）

`click(aim=True)` 名义上会把误差收到 12 px 以内，实际回执是
`pointer_err=16.9px corrected=0` —— 误差超了容差，**纠偏却没执行**。

根因：`_find_pointer_near` 靠**帧差**找指针，在探针页（黑底 + 红网格）上经常返回
None，`_confirm_pointer` 拿不到落点就直接放弃。于是用户拿到的是开环的 6–40 px。

修法（0.9.76）：
1. **探针真值优先**：探针在前台时直接用二维码读到的位置（0.01 pt），帧差只作兜底；
2. 帧差失败时再轻推一次重试（原来只推一次就放弃）；
3. 误差换算用**本机画面宽高**（原来写死 500×1080，608 宽的机器低估 x 误差 18%）。

⚠️ **读到「飞行中」的位置会让纠偏反而更歪**：移动后立刻读探针，QR 里的 AGE
（距上次 hover 多久）很小 = 指针还在飞，读到的是中途值。2026-10-30 实测：
这样算出 31 px 的假误差 → 纠偏移到错的位置 → 残留 31 px。判据必须和校准一致：
**AGE ≥ 150 ms 且帧是这次调用之后拍的**。修好后同一批点 4.9–10.8 px。

⚠️ 纠偏的精度上限就是表本身的精度：一个小纠偏（十几 px）残留仍有 4–6 px 量级
（实测 7.4 → 3.8 px），**大误差才收益明显**。

### §2.39b 圆角机上「加密/按曲率摆点」不解决问题（2026-10-30）

模型评分说自适应摆点能把最大误差从 18–43 px 压到 2–26 px（3–4 倍），
**真机两轮都更差**：自适应 10.79、12 档密表 11.99，而现表 5.89–6.39 px。

同一命令重复 10 次：8 次完全相同、最大跳 6.7 px（SE 是 0.00）。
也就是说 6 px 误差里有一部分是**随机会跳**，静态表消不掉。

结论：别再在表的形状上投入，圆角/高速设备走**闭环纠偏**。

⚠️ 做这类实验要注意：**实验里构造的非均匀表会被载入清洗改动**
（`trim_first_stop` 假设局部线性，而曲率自适应恰好把点放在拐点上）。
`Device(calib=tmp)` 之后再覆盖 `dev.calib["corners"]` 才能拿到干净对照。

### §2.39c 校准验证从不测边缘（2026-10-30）

`validate()` 的目标只取 0.15–0.95，**边缘从来不测**。所以「整条顶带打高 50 px」
能在随机 16 点验证报 0.75 px 的情况下潜伏好几天。

0.9.76 起加 `band_check()`：每角 2 点，专测「表第一档 → 停车点」那段**外推区**的中点
（正是坏档出事的地方，而且天然可达，不会把「不可达」记成误差），阈值 25 px。

### §2.39a 圆角屏 6 px 的不是表，是曲线饱和（2026-10-30）

同一套「四角 + 单轴」在这台上重校准，单点验证中位 **9.3 px**（直角屏 SE 是 0.75）。
实测增益 **1.32 → 0.68 px/单位**：同样的大步长、同样的固件节流，后半程只有一半 ——
iOS 的「最大速度」在限制长位移，所以曲线是**饱和型**，不是直线。

后果：表只能采到 5–7 档（指针很快贴边、自动截断），最陡那一段只有 1–2 个点。
历史数字「中部 5.8 / 四角 26.6 px」就是这么来的，**不是角的几何问题**。

对策：这类设备不要减档位（实测 3/4 档更差：7.56 vs 6.25 px），
应该在饱和段加密，或者直接用闭环兜最后几 px。

### §2.39 校准第一档被记成 4 倍，整条屏幕顶边打高 50 px（2026-10-30）

**症状**：iPhone SE（608×1080，直角屏）上，**目标 y < 0.12 全部打高 45–54 px**，
`clamped / approximated` 都是 False（不是钳位），其余 88% 屏幕只有 1.1 px。
分层看：S1 中心 1.08 px、S2 边带 2.06、**S3 近角 21.35**、S4 远象限 1.26。
所以「四角最差」其实是「顶边一档数据错」——四角目标恰好都落在 y<0.13。

**根因**：TL/TR 的 y 表第一档记成 `[30, 0.0742]`，实测真值 `[30, 0.0287]`。
0.0742 对应的真实位移是 ~120 单位，是 30 的 4 倍。`units_for` 对所有
`y < 0.0742` 的目标都拿这一档外推，第一档到第二档（300 单位）那一段斜率整段失真，
误差一路衰减到 y=0.1652 处归零。

**为什么旧检查没拦住**：那个点**单调、不离群、也不违反表尾规则** —— 错的只是斜率。
`clean_table` 管的是「比后一个还远」这类非单调坏点，管不了「单调但斜率错 4 倍」。

**修法**（源码已加，随 0.9.74 发布）：
1. `calibration.trim_first_stop()`：第一档必须落在「第二、三档连线」外推的
   ±0.03 屏高内，否则丢弃（丢弃后 `units_for` 用第二、三档外推，线性段上等价）。
2. 阈值 0.03 的来由：**数据错**的量级是 0.045（49 px），而**圆角/加速曲线让第一档
   天然偏一点**的量级是 0.012（13 px，500x1080 圆角机的实测最大值），中间有裕量。
   ⚠️ 圆角屏的第一档本来就该偏 —— 别把几何效应当数据错剪掉。
3. 当场修数据：把该档改成实测值即可，**不必重跑整轮校准**（本轮 34.9 → 1.6 px）。

**教训**：校准的收尾验证只有随机 4 点，抽不到这种「一条带状区域」的系统性错误。
要么按「最坏区域」定点验（顶带/底带/左右带各取几点），要么就靠这种**结构自检**。

## 3. 坐标与点击

- **布局会漂移**：信息 App 新建按钮实测 `y 0.885 → 0.935`；每次按最新截图取坐标。
- **`changed=true` 不代表成功**：hover 只有约 90 px；真实界面变化通常 > 1000 px。
  用 `min_change_px`（`click_text` 默认 500）。
- **顶部 6% 是 `Device.changed()` 的盲区**（避状态栏时钟）：TL/TR 停车点在 y≈3%，
  校准里不能用它判变化，要用 `_diff_pixels`。
- **边缘够不到**：BR/TL 停车点离边约 3–10%，`x>0.96` 的按钮可能点不到；必要时换角或截图确认。
- **底部 6% 精度下降**（`y>0.94`）：点控件上沿，或用键盘。
- **圆角不可达带**：iOS 把指针中心夹在圆角内，`x<0.15 且 y>0.97` 一带物理点不到；重试无意义。
  几何模型见 `control/corners.py` + `corner_profiles.json`；`click` 返回 `predicted` 供对照。
  换手机/分辨率先 `python control/measure_corners.py --device "…"`。（§6.2）
- **点击默认 `aim=True`**：先找指针纠偏，多花 1–2 s；`pointer_err` 从个位数突然变成 ~110 px
  说明表已经不对，别硬补偏移，重校。
- **右键是「应用相关」的**：备忘录列表能弹菜单，部分第三方列表无响应。
  `click(x, y, button="right")` → 固件 `click 2`；工具 schema 要重启 MCP 才出现 `button`。
- **关闭上下文菜单别点「看起来空白」的地方**：iOS 菜单项是整格命中。左下角的 `(0.88,0.42)`
  看起来像面板边缘，其实落在「删除」格里（2026-10-23 真删过一条）。关菜单用 `esc`
  或点**远离面板**的空白（如 `y>0.85`）。
- **`aim` 会误判，别迷信 `pointer_err≈0`**：底部区域实测实际落点比目标低约 30 px，
  而 `pointer_err` 只有 1.0 px（它把界面里的灰色圆/阴影当成了指针）。`y>0.9`、小图标、
  或连续 `changed=false` 时，把目标**上移 0.02–0.03** 再点，并重新截图核对。
- **滚轮能用，但很小**：`scroll N 0` 每份报告只走约 4–8 px，**N 被忽略**（-1/-5/-20 一样），
  连发才累加；好处是无惯性。整屏翻页仍用分段拖拽（`dy`），微调走 `scroll(fine=N)`。
  工具层已把 `fine` 取反，**统一为「正数 = 向上/更早」**；个别表面方向相反时用
  设置 → 交互 → 滚轮方向 翻转，别改代码。
- **滚轮跟着指针走**：iOS 只滚「指针下方」的滚动视图；指针停在工具栏时 `moved_px=0`。
  `scroll(fine=…)` 会先把指针停到屏幕中央。
- **拖拽/滚动松手前必须停住**：抬手瞬间 iOS 按最近速度结算惯性，边走边松会被当成甩动。
  `drag`/`scroll` 现在松手前停 1.30 s + ease-out；松手后按**像素差**连续 2 次无位移才截图
  （最多约 3 s）。**别用字节比对**——同画面重编码后 JPEG 字节也不同。

## 4. 校准

- 校准前先测**投屏延迟**（实测中位 223–355 ms），等待时间不短于「延迟 + 80 ms」。
- **>1200 ms 直接拒绝校准**（每档读到的是移动前的画面，表会偏短）。>300 ms 先修 Wi-Fi。
- 校准表只有一个权威文件：`~/Library/Application Support/HIDBridge/calib.json`（`HIDBRIDGE_CALIB` 可覆盖）；
  仓库里的 `control/calib.seed.json` 只是参考，**0.9.67 起不再自动安装**。
- 动作前会按 mtime 自动 reload；`calibration_status.stale=true` 说明文件比内存新，
  调一次 `calibration_reload`。**校准完不需要重启 MCP**，但要确认 `measured_at` 变了。
- **校准失败/取消不再作废**：每测完一个角（连停车点）就写 `calib.wip.json`，向导给
  「继续校准（从 XX 开始）」。正式表仍然四角齐了才写；临时档案不参与点击计算。
  屏幕尺寸/视频源变了或超过 24 h，临时档案整份作废。
- **`calib.json` 的 mtime 变了不等于表变了**：App 启动/切换档案时的「匹配校准」会**重写**文件
  （mtime 变、`measured_at` 与 `refs` 原样）。判断表有没有换看 `measured_at` / `refs`。
- **失败文案按四类给下一步**（探针 / 画布（锁屏、切 App）/ 链路 / 精度闸门），原始异常只进日志。
- **时长**：直角屏走**精简档**（x 3 档 / y 4 档）**≈ 8 分钟**；圆角屏、平板仍是全档位，约 **20 分钟**
  （每档 ~17 s，19 档/角）。续校按「≤5 分钟/角」估。向导里那句「15–30 分钟」是保守值。
- **顶角上行距离起点是占位值 400**，不是几何值：`tune_top_park()` 会按真值调到 3%–12%
  （实测 400 → 1093.5）。**别**把它换成 `0.94×屏高` 的估算当起点，那可能一上来就把指针顶到 y=0。

### 4.4a `codesign` 报 "A timestamp was expected but was not found"

不是代码问题：`--timestamp` 请求 Apple 时间戳服务器那一次失败了。**先原样重试一次**（实测 23:20 失败、
23:29 通过）；还不行就单独验服务器：
`codesign --force --options runtime --timestamp --sign "<ID>" /tmp/x.dylib`。

**顺带**：`build_release.sh 2>&1 | tee log` 的退出码是 `tee` 的，构建失败也显示成功。
判断成败要 `grep "status: Accepted"`。

### 4.4b `github.com:443` 不通怎么发版

同一台机器 `curl https://github.com` 超时、`https://api.github.com` 正常 → `git push` 全挂，
但 `gh release create/upload` 照常（gh 走 API）。

```bash
sha=$(gh api repos/<o>/<r>/contents/README.md --jq .sha)
b64=$(base64 -i README.md | tr -d '\n')
gh api -X PUT repos/<o>/<r>/contents/README.md \
  -f message="docs: …" -f content="$b64" -f sha="$sha" -f branch=main
```

校验更新用 `gh api .../contents/<path> --jq .content | base64 -d`，**别用 raw.githubusercontent.com**。

### 4.4c `notarytool` 卡在 "Conducting pre-submission checks" 且 `history` 查不到

= **DMG 还挂在系统里**（`/Volumes` 里看不到也可能仍在）。手动补公证时绕过了脚本的 preflight，就会中招。

```bash
hdiutil info -plist            # 找 image-path + system-entities 的设备号
hdiutil detach /dev/diskNN -force
```

### 4.5 UVC 采集卡（HDMI 有线投屏）

| 现象 | 根因 | 规避 |
|---|---|---|
| 整屏绿色雪花、画面隐约可见 | 采集卡发 **UYVY（`2vuy`）**，AVFoundation 转 BGRA/NV12 在这块卡上是错的 | 取原生 `2vuy` 自己解释；ffmpeg 用 `-pixel_format uyvy422` |
| 找黑边全失败 | `2vuy` 是 **Cb Y Cr Y**，亮度 Y 在**奇数字节** | 扫 `p[y*bpr + x*2 + 1]` |
| OCR 在 888×1920 上更差 | Vision 对大字号不敏感 | 送 OCR 前缩到 ~600 宽；坐标仍归一化 |
| 画面横过来了 | 采集卡的「竖屏模式」把内容旋转 90° | 别只用宽高比；按「文字行横竖 + 时钟位置」判，`uvc-frame --rotate ocr` 自动转 |
| 第一帧撕裂 | 刚 startRunning 的半帧 | 丢掉前 2 帧 |
| 拔卡后画面变成「摄像头看到的房间」 | 旧逻辑取「第一个外部摄像头」，iPhone 连续互通相机也是 external | 只认 `modelID` 含 `uvc` 的；排除 FaceTime/iPhone/iPad；找不到就报错，不回退摄像头 |
| `UVC capture exited (code -6)` 每秒一条（没插卡也一样） | macOS 13.x：helper 用了 14 的 `external` API，dyld 直接 abort | 0.9.66 起 macOS<14 不拉进程、5→300 s 退避；只用 AirPlay 可忽略 |
| 换源后点击整体偏 | 不同源尺寸/裁切不同 | 档案键是 `源:分辨率`，切源按 `X-Video-Source` 自动启用 |
| 双开时只有一路实时 | **iOS 同一时间只维护一个外接显示会话** | 所以不做自动切换：手动选源，另一路只做监视 |
| 采集卡插着但 HDMI 没接，AI 仍当有画面 | 卡会输出纯色底图，`live` 仍 true | 灰度标准差 <6 连续 3 s → `signal=false`（不自动换源） |
| 拔卡后插回不恢复 | 旧 helper 不退出 | 看门狗 5 s 无帧且 `isConnected=false` → 退出码 3；服务端每 10 s 重试（实测 10 s 恢复） |
| 日志里两套 `AirPlay receiver started` | GUI 刚启动、`:8890` 还没监听时 MCP 也拉了一套 | `server.lock` + 先等 2 s；抢不到锁就等对方 API |
| App 请求相机不弹窗、直接拒绝 | hardened runtime 缺 `com.apple.security.device.camera` | entitlements + `NSCameraUsageDescription`，缺一不可 |

### 4.6 从 GitHub 下安装包：直链废、API 直链慢

- `github.com/.../releases/download/...` **直接超时**，别当下载地址；
- `api.github.com/.../releases/assets/<id>`（带 `Accept: application/octet-stream`）能下，但实测 ~40 KB/s
  （97 MB ≈ 40 分钟）；
- **结论**：MCP 只把 `https://github.com/jianghui1974/Quileg-HID/releases/latest` 交给用户点，
  **不下载、不安装**。曾实现过的下载/安装（`bd4df7f`）已删除。

## 5. 数据安全（真实踩过）

- **误删备忘录**：`文件夹 → 最近删除 → 编辑 → 选中 → 文件夹图标 → 备忘录` 可恢复（30 天内）。
  **iOS 17 的“最近删除”没有单独的「恢复」按钮**（只有 移动/删除），别去找。
- **不要凭截图判断文本被改**：长行会软换行，看起来像被回车拆开；让用户确认或选中复制比对。
- 修改用户数据（笔记、联系人、设置）前先得到明确同意；测试内容写在自己的测试笔记里。
- **不要长按敏感页面**（备忘录/密码/邮件）：iOS 的预览卡片会明文展开正文，截图会进模型上下文。

## 9. 便宜板（ESP32-S3-N16R8）：XMC Flash 的坑

> 背景：XIAO 较贵，用 YD ESP32-S3-COREBOARD V1.4（N16R8，¥20 级）做实验。
> 固件统一为 `s3_16m_universal`（见 `firmware/hid_bridge/src/board.h`）。
>
> ⚠️ **16 MB 是产品决定，不是可商量项**（2026-10-30 定）：后续板载摄像头需要大分区余量，
> 所以硬件统一锁死 16 MB、避免出现「8M 版 / 16M 版」两套固件。**不要为了兼容 8 MB 板去改分区表或加分支。**

### 9.1 烧官方 16M 镜像后无限重启

- **现象**：串口每 ~0.3 s 刷 `XMC flash startup fail` / `failed when running XMC startup flow, reboot!`，
  BLE 名不广播，App 看不到板子。
- **根因**：IDF 5.4+ 的 bootloader 用白名单判 XMC（MFID `0x40/0x41/0x50`），这颗 **XM25QH128A 是
  MFID `0x70` / CPID `0x18`** → 被强制复位一轮仍认不出 → 重启。Espressif 官方表态不修
  （[esp-idf#18947](https://github.com/espressif/esp-idf/issues/18947)）。
- **规避**：`firmware/tools/patch_xmc_bootloader.py`（16M profile 构建时自动跑）把该函数改成
  "立即返回 OK" 并重算 checksum + SHA256；对非 XMC 芯片是恒等变换。
- **判断命令**：`esptool flash-id` 看到 `Manufacturer: 20 / Device: 7018` 即确认。

### 9.2 用 App 刷机会报串口噪声

`Invalid head of packet (0x81/0x30): Possible serial noise` —— 这块板的 CH343 在 460800/921600 下不稳。
**刷机用 230400**（`app/core/firmware.py` 已改默认；115200 也稳）。

### 9.3 NVS 配置写不进去（已解决）

`cfg` 回 `ok saved`、当场能读回，**重启后丢失**。根因是 **Flash 模式不匹配**：Arduino-ESP32 默认按
QIO 编译，这颗 XMC 的状态寄存器写不进去，bootloader 回退 DIO，但运行期 `esp_flash_read` 仍按 QIO 发
读命令 → 读数据分区一律 `0xFF`（写是好的，所以「写成功、读不到」）。

- **规避**：16M 镜像**显式用 `FlashMode=dio` 编译**（`firmware/build.sh` 已固定）。
  只给 esptool 加 `--flash-mode dio` 改镜像头**不够**，必须重编译 bootloader。
- **判定**：固件里 `esp_partition_write` 64 字节后立刻 `read` 比对（`match=0` + 全 `0xFF` 即是）；
  同一地址用 esptool 读却是对的 → 写没问题，是固件读路径坏了。
- **验证**：`flashprobe` → `match=1`；`cfg` 写 → 重启 → `cfg?` 仍在。
