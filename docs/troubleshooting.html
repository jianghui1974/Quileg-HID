排障与兼容性

真实踩过的坑、设备兼容矩阵、已知问题。

目的：把每次实测踩到的坑，变成下一位 AI 的检查项。 维护规则：每做一个新任务，回填一条「现象 / 根因 / 规避 / 证据」；配方级的步骤同步进 给 AI 的操作手册。 最后更新：2026-10-23（新增 §2.2 语音桥） 相关：给 AI 的操作手册（操作手册）· 接入 AI（MCP）（接入）

0. 开工 30 秒检查

status()      → device / screen / calibrated
screenshot()  → 当前页、列、键盘状态、是否有弹窗
  • screen=false：等 2 s 再看一次；仍 false 就请人重开「屏幕镜像」，不要反复重试。
  • calibrated=false：不要盲点，先跑校准。
  • 截图可能晚一帧：每个动作后多截一张再判断，否则会把「已提交」看成「还在输入」。
  • 主屏有多页、每页列数不同：同一坐标在不同页可能是不同 App，先看截图再点。

iPhone 端两个总开关（每次新设备/换机必查，埋得很深） 1. 辅助触控必须开：设置 → 辅助功能 → 触控 → 辅助触控。不开就没有鼠标指针， 所有 click/move 都像“没反应”。 2. 鼠标键「使用主键盘」必须关：设置 → 辅助功能 → 触控 → 辅助触控 → 指针设备 → 鼠标键 → 使用主键盘。开着时键盘被当成鼠标：i j k l m o u 7 8 9 . 不落屏、 回车不换行而是弹菜单、指针乱跳。这是 2026-10-22「11 个字符永不落屏」的真正原因， 关掉立即恢复，不需要重启手机。

反模式：别自己发明流程（会浪费大量时间，而且不可靠） - ❌ 手改 calib.json / 自己补像素偏移 / “这次先 +0.02 试试”——校准错了就 calibration_request； - ❌ 不用 click_text 而靠目测坐标反复盲点；不用 scroll(fine) 而自己拼拖拽； - ❌ 连续 changed=false 不换目标、不查日志，闭眼重试； - ❌ 绕过 MCP 直接 curl /api/raw 或写脚本操作手机（排障例外，要说明）； - ❌ 自己跑校准向导（必须用户点「开始」）； - ❌ 遇到问题先怀疑固件/重装 App，而不是先看 status / app_logs。 先翻 AI_GUIDE §1.0 的工具表，再动手。摸索 10 分钟不如查表 10 秒。

0.1 新设备 / 新场景：先建立基线

用户可能换 iPhone / iPad、换 iOS 版本、换指针大小、换网络。同一套坐标、滚动距离、返回手势不要跨设备复用。

第一次接触一台设备或一个 App，先记下：

项怎么取
设备 / 系统用户告知，或从屏幕「关于本机」看
指针大小设置 → 辅助功能 → 触控 → 辅助触控 → 指针控制
镜像分辨率status() 的 aspect、截图尺寸
校准calibrated + control/calib.json 里对应的 profiles 键
投屏延迟校准向导第一步会测（这台 0.53 s）
BLEstatus 里 connected/encrypted/sub/kb/ms

然后用计算器 7+8=15 验证这张表是否适合当前设备。不要凭“上次也是 iPhone”就直接操作。

基线写进 §6.1，任务中的新发现写进对应小节；下一个 AI 先翻这里，再动手。

2. 输入（中文 / 英文 / 标点）

  • 九宫格不可用：硬件键盘连接时 iOS 隐藏软键盘，九宫格点不到；即使能显示，每键 4–7 s。用全键盘。
  • 候选选择用数字键 1–9；空格只移动高亮，不提交。
  • 候选顺序不固定：荀彧 是第 3 个、使 是第 4 个、至 是第 4 个。按数字前先看候选内容。
  • 英文候选是标签符号：拼音模式下打 abc，选 ABC/abc 插入的是灰色胶囊（退格整块删除），不是普通文本。要普通英文先 ctrl+space 切英文输入法。
  • 标点宽度不统一：输入 123,456.789! 实际得到 123,456.789！（逗号/句点半角、感叹号全角）。不要假设 1:1。
  • 整句拼音可行：woxihuanbeijing → 「我喜欢北京」；nihao → 「你好」。名句命中率高，冷门内容要分段。
  • 生僻字用组词法：xunyu→荀彧→←退格→⌘→；caojianrenming→草菅人命→删字→⌘→。
  • 删字后必须回行尾：退格只删字符不移动光标；不 ⌘→ 就继续输入会插到目标字前面（实测 9菅 vs 菅8）。
  • 软键盘不显示 ≠ 没聚焦：看蓝色边框/光标，或用 Tab 切焦点。
  • type_text 仅接受 ASCII：中文通道已移除；中文改用拼音 + 截图/OCR 判断候选 + click_text 点选，不依赖任何外部服务器。
  • 切 App：iPhone 上没有 cmd+tab（2026-10-22 实测 cmd+tab / shift+cmd+tab 都无反应，iPadOS 未验证）。 用 cmd+h 回主屏 → cmd+space 搜名字打开；cmd+h 本轮 2/2 生效。App 内标签可试 cmd+1–cmd+9。
  • Tab 会被中文输入法吃掉：弹出候选栏，不是焦点导航；先 ctrl+space 切英文。
  • Enter 常只提交候选词，不激活界面元素；Spotlight/备忘录里失败时改用 click_text。
  • type_text 含非 ASCII 会直接报错：这是预期行为；先改写拼音，再用 OCR 点候选。

2.1 部分字符不落屏 / 回车弹菜单：鼠标键「使用主键盘」被打开（2026-10-23 更正）

现象：type_text、App 软键盘、POST /api/raw {"text":"type i"} 三条路都一样——在备忘录/Spotlight 里 下面 11 个字符从不落屏，其余字母数字、大小写、标点、顺序全部正常：

i j k l m o u 7 8 9 .
usage: 0x0C 0x0D 0x0E 0x0F 0x10 | 0x12 | 0x18 | 0x24 0x25 0x26 | 0x37

同时还有两个伴随症状：回车不换行，而是弹出功能选项/菜单；指针有时自己乱跳。

根因（2026-10-23 用户定位）：iPhone 的 设置 → 辅助功能 → 触控 → 辅助触控 → 指针设备 → 鼠标键 → 使用主键盘 被打开了。 键盘被系统当成鼠标：i/j/k/l 移动、u/o 点击、7/8/9 方向、. 等，Return 被当作点击。 这 11 个正好是鼠标键的键位——不是固件坏，也不是 HID 键位状态坏。

恢复：把 使用主键盘 关掉（不需要时把 鼠标键 也关掉），立即恢复； 不需要重启 iPhone、不需要重配对。

前置：辅助触控 必须开着，否则 iPhone 上根本没有鼠标指针（见 §0）。

为什么之前误判：2026-10-22 那次靠「重启 iPhone」恢复了，于是归因为“HID 键位状态坏了”； 实际是设置开关的问题（重启/重配后开关被重置或后续被关掉）。现在以开关状态为准。

同一块板 + 同一固件，只换宿主（当时的证据，结论仍成立——手机侧设置问题）：

宿主结果
macOS（Sublime Text）✅ aib ijklm 789. 14 个字符全落屏
iPadOS 18（备忘录）✅ hijklm 全部进入拼音组合
这台 iPhone（iOS 18）❌ 11 个全丢（当时鼠标键开着）

已排除（别重复走这几步）：

假设实测结果
固件 kLayout 写错 / 出厂镜像旧源码表与 app-16m.bin、factory-16m.bin 逐字节一致；key i 返回 ok（不是 err unknown key），说明运行时映射非零
按压时长太短、被 iOS 合并type（10 ms）与 key（40 ms）同样丢

排查顺序（以后照这个走，别先怀疑固件）：

  1. type_text("aib") 自检，确认是「部分字符」还是「完全打不进去」；
  2. 换宿主（Mac 或 iPad）打同一串：换了就好 = 手机侧问题，不要动固件、不要重校准；
  3. 先查手机两个开关：辅助触控 = 开；指针设备 → 鼠标键 → 使用主键盘 = 关；
  4. 仍不行再：重启 iPhone → 重新配对 → 还原键盘词典 → 第二台 iPhone 对照。

2.2 语音桥：Mac 朗读 → 手机听写（2026-10-23 实测）

用途：中文输入最慢的是点候选；让 Mac 用 speak() 朗读、手机输入法听写，直接上屏。 speak → /api/speech → 系统 say。

起停方式：双击 Control 开始，单击 Control 停止（不需要点屏幕麦克风）。 MCP 调用：dictation("start") / dictation("stop")（0.6.0 起）。 它会先按一次 Shift 唤醒 HID 键盘，再双击/单击 Control —— iOS 会吞掉空闲后的第一次按键， 直接 key(combo="ctrl", repeat=2, gap_ms=60) 常常只算一次 Control，听写起不来（2026-10-23 实测）。

  • 前提：手机 设置 → 通用 → 键盘 → 听写 → 听写快捷键 = Control（选项只有 Control / Command / 无）；
  • 实测两次按下间隔 60 ms 有效；150 / 350 / 500 ms 都没反应，固定用 60 ms；
  • 光标必须在文本框里；软键盘开或关都行（关了也能起）；
  • 正在听的样子：状态栏橙点 + 光标旁黄色小麦克风 + 键盘右下角麦克风变深色停止键； 黄色小麦克风很小、容易被忽略——它是“正在听”的唯一提示。

2.3 Intel 版 OCR：.accurate 不可用时自动降级 .fast（2026-10-24 实测）

现象：Intel 包（x86_64）调 ocr / click_text 时，Vision 的 .accurate 识别直接报错 TextRecognition.CRImageReaderError 9，ocr-text 返回 vision request failed，OCR 全不可用。

实测（同一张图，同一个 ocr.swift）：

请求arm64x86_64（Rosetta / Intel 代码路径）
VNDetectRectanglesRequestOKOK
VNDetectBarcodesRequestOKOK
VNRecognizeTextRequest .fast（rev 1/2/3）OKOK
VNRecognizeTextRequest .accurate（rev 1/2/3）OK全部 CRImageReaderError 9

也就是说不是 Vision 整体坏掉，而是 .accurate 用的那套 TextRecognition 模型在 x86_64 上跑不了 （macOS 26 时代的模型只带 ARM 内核的可能性很大；真 Intel 机器上很可能一样）。

处理：control/ocr.swift 先试 .accurate，失败后自动用 .fast 重试，并在 stderr 打一行 ocr: accurate 不可用，已降级为 fast。功能不中断，准确率略降（短标签/数字仍可用， 长文与生僻字更容易错；要点选候选时先用 ocr() 看清结果再点）。

判断自己是不是这种情况：app_logs(grep="ocr") 或直接跑 "Quileg HID.app/Contents/Frameworks/control/bin/ocr-text" <图> 看有没有那行降级提示。 arm64 机器上不会出现。

没做：给 Intel 换第三方 OCR 引擎（体积、许可、中文质量都要重评）。 真机上如果 .fast 也不够用，再考虑。

2.4 iPad「锁屏」其实是顶边面板（2026-10-24 真机定案）

现象：被控设备是 iPad（iPadOS 26）时，指针移到左上角/顶边，屏幕变成「锁屏」的样子， 校准与点击全部中断。

结论（真机实测）：不是锁屏，是 iPadOS 26 的顶边手势——指针碰到屏幕顶边（y≈0）时， 左半区拉下通知中心、右半区拉下控制中心；两者都是全屏毛玻璃 + 大时钟，看起来和锁屏一样。 Esc 能关闭通知中心，点空白能关闭控制中心（两者都实测过）。

证据（2026-10-24，iPad + 0.7.0 + 0.9.32）：

动作结果
release 7 → move -2000 -2000（纯移动，无点击）出现通知中心（x≈0.22）
move 4000 -2000（到顶边右半）出现控制中心
move -2000 0 / move 2000 0（左/右边，y≈0.45）正常，无面板
move 2000 2000（右下角）正常，无面板
40 小步慢速走到顶边仍出现控制中心（所以是位置触发，不是速度）
key esc面板关闭（通知中心/控制中心都试过）

为什么每次都会踩到：Device.goto_corner() 的 home（40 × move -127,-127）必然把指针顶到 (0,0)，所以每一次移动/点击的归位都会碰顶边。iPadOS 26 的正常鼠标用户也会遇到同样的事， 不是固件、不是按键、不是校准。

已排除：左键卡住（release 7 后仍复现）、点击（全程无 press/click）、 触发角 Hot Corners（四个角都是「无」）、停留控制 Dwell（已关）、自动锁定（设为「永不」， 且 60 秒空闲对照没有锁）。

规避（0.9.33 起已内置）：

  1. 看错时先按 Esc：能关掉就是面板，不是锁屏（通知中心/控制中心都能关）；
  2. 归位改成「底部锚定」：底边 + 左右边（实测安全）夹住指针，顶角从底边上行 固定单位到达，完全不走 home，所以不会再碰 y=0。校准档案里多了三个字段： park: "bottom"、park_up: {TL, TR}（顶角上行单位）、park_lift（底角上抬，避开程序坞）；
  3. 旧档案仍走旧路径（home），所以 iPhone 等设备不用动；iPad 要重新校准一次才会切到新模式；
  4. 校准期间别碰设备；自动锁定设「永不」。

实测（iPad 1554×1080，2026-10-24）：停车点 TL(0.019,0.056) / TR(0.979,0.056) / BL(0.027,0.880) / BR(0.977,0.867)，park_up 1130/1116，16 个随机点中位误差 25.9 px、 最大 76.6 px，全程无面板。

教训：iPad 上的「锁屏」先按 Esc 试一下——能关掉的就不是锁屏，是系统面板。

底部程序坞（2026-10-24 实操发现）：底部锚定会碰屏幕底边，iPad 的程序坞随即弹出， 盖住最下面约 18%。此时点击「计算器 =」「键盘底行」会命中程序坞，而不是 App。 规避（0.9.34 起内置）：目标 y>0.75 时，先移到画面中部让程序坞收起（等 0.9 s），再下到目标； 比停车点更靠下的目标（底部 ~13%）钳到停车点高度——那一段本来也没有分段表。 实测修复后 7+8=15、9×9=81 均通过；AirPlay 截图会晚 0.3–0.5 s，验收等 2 s 再截。

窗口化 vs 全屏幕 App（2026-10-24 用户实测）：iPadOS 26 的「窗口化 App」模式里， 指针移到窗口边缘会变成缩放/移动光标，顶部还会出现菜单栏，行为更难预测； 切到「全屏幕 App」后指针形状稳定。建议校准与日常使用保持同一种显示模式 （设置 → 多任务与手势 → 全屏幕 App）。全屏幕模式下实测点击误差 28–36 px，与校准表一致。

2.5 底部锚定的钳位只判了一个方向（0.9.34 回归，2026-10-24）

现象：iPad 上点屏幕上半部分，指针落在画面顶端（y≈3%），点击完全无效； 没有报错，calibrated=true，changed 也可能是 true（指针动了）。

根因：0.9.34 的程序坞修复给 move_to 加了钳位，只判一个方向：

if ref_y is not None and y > ref_y:
    y_eff = ref_y     # 只考虑"比停车点更靠下"

底部锚定档案里 TL/TR 的停车点在顶边（ref_y ≈ 0.05），于是任何 y > 0.05 的目标都被钳到 0.05，纵向命令根本不发（抓命令可见只有横向 move 772 0）。

为什么验收没发现：计算器按键多数走 BR（nearest_corner 取距离最小）， 钳位条件 y > 0.86 不成立，所以 7+8=15 照常通过。验收要覆盖四个象限。

修法：两侧都判——底边停车点钳"更靠下"，顶边停车点钳"更靠上"（0.9.35）。 真值验证：同一张表，目标 0.5,0.3 从 210 pt 降到 17 pt。

判定方法：在 iPad 上点一个上半屏目标，如果落点贴顶边且 changed=true，先查 move_to 发出的纵向命令是不是空的。

2.6 误选「仅升级」后 Wi-Fi 配不上（分区表不匹配，2026-10-25 实测）

现象：板子残留别的分区布局（例如以前刷过别的项目），在固件页选「仅升级固件」→ 刷写成功、固件也能启动，但到初始化阶段Wi-Fi/服务器配置写不进去。

根因：「仅升级」只写 app0（0x10000），分区表原样保留。如果板子上的 nvs 不在 0x9000 / 大小不是 0x5000（本固件的布局），NVS 就落在固件以为之外的区域， 配置写入必然失败——不是「板子没初始化」，而是分区表不是这一套。

本固件的分区表（factory-16m.bin 内嵌，0x8000 起）：

nvs      0x9000  0x5000
otadata  0xe000  0x2000
app0     0x10000 0x140000
app1     0x150000 0x140000
spiffs   0x290000 0x160000
coredump 0x3f0000 0x10000

修法（0.9.38 起）：刷写前读 0x8000 的 4 KB 分区表并解析（parse_partition_table / layout_matches）。只要 nvs 或 app0 对不上，只允许整包刷写，并在界面上说明原因：

分区表不符（nvs 在 0x1f000/0x6000，本固件要求 0x9000/0x5000）：只能整包刷写

检查只在「检查板子」时做一次（多读 4 KB，约 1–2 秒）。

2.7 8 MB 板：「仅升级」报成功但 Wi-Fi 配不上（2026-10-25 已加防呆）

现象：8 MB 的板子（例如只焊了 8 MB flash 的 S3）用「仅升级固件」刷 16 MB 布局的包， esptool 报写入成功、校验通过，固件也起得来，但配网永远失败——和 §2.6 同一类结局， 只是根因在 flash 容量而不是分区表内容。整包则会在 erase_all 之前被 esptool 按尺寸拒绝。

根因：App 刷写时一直用 --flash-size keep，manifest 的 flash_size: "16MB" 只用于 界面展示，从没读过板子的真实容量。8 MB 上 app 只有 1.17 MB，尺寸校验当然过得去。

修法（2026-10-25，未发版）：FirmwareFlasher._write() 先跑一次 esptool flash-id，解析 Detected flash size: 16MB，与 manifest 比对：

  • 不符 → 在 write-flash 之前终止（不擦不写、flash 原样保留），UI 显示「已拒绝刷写」；
  • 读不到（老芯片 / secure download mode）→ 不拦，仍由 §2.6 的分区表检查把关。

单测用 mock.patch 替掉 _run_esptool，断言拒绝发生在 write-flash 之前 （app/tests/test_firmware.py::FlashSizeGuardTest）。

2.8 竖屏 iPhone：探针 HUD 被裁掉 → 校准静默退回帧差（2026-10-25 定位并修复）

现象：iPhone（500×1080）自动校准跑到第 55 个点（BR y=30）报 「测不到指针（画面在动/指针不可见）」，13 分钟作废；但同一次校准前面 54 个点都过了。 屏幕看着完全正常、探针 HUD 清清楚楚。

根因：control/probe.py 的 HUD 裁剪框写死成画面比例的 (0.01, 0.03, 0.60, 0.62)。 HUD 的宽度是按 pt 固定的（约 350），所以它在画面里的占比随屏幕宽度变： 375 pt 的 iPhone 竖屏上值列排到 x≈0.91，1180 pt 的 iPad 横屏只有 ≈0.55。 固定 0.60 在 iPhone 上把 PT 行第二个数和 SIZE 的「375 x 812」切掉 → parse_pt / parse_size 都返回 None → pointer_fraction() 永远 None → 连续 4 次后 _no_probe = True，整轮改走帧差却没有任何提示。

证据（同一帧）：

裁剪parse_sizeparse_ptOCR 文本
(0.01,0.03,0.60,0.62)NoneNone'375x'、只有 '340.35，'
(0,0.02,1.00,0.70)(375.0, 812.0)(340.35, 334.87)'375 x 812'、两个数都在

修法：_hud_box(w, h) 按方向给右边界（竖屏整幅、横屏 0.62），下边界放到 0.70 （HUD 到 SCALE 行约 0.63）。另加一条：探针失效时 progress("探针读不到，本次改用帧差 （精度会下降）")，别再静默降级。

回归测试：app/tests/test_probe_reader.py::HudCrop，用真机帧 app/tests/fixtures/probe-hud-iphone-500x1080.jpg 断言能读出 (375, 812) / 340.35, 334.87 （修复前这条会拿到 None）。

教训：探针"不报错、只是变慢变差"是最危险的状态——它让 iPad 上的好结果掩盖了 iPhone 上的完全失效。凡是"有真值就用真值、没有就回落"的分支，回落时必须留痕。

2.9 表中间留了个洞：内点离群，随机验证看不出来（2026-10-25 实测）

现象：同一台 iPad、两台 Mac 各跑一次自动校准。本机 中位 15.3 px / 最大 36.6 px， 另一台 17.3 px / 138.1 px。中位几乎一样，但两张表逐点对不上，最大差 272 px。

根因：内点离群——某一档只挪了一点点（或挪过头），而两侧档位都正常：

机器坏点本机值正常趋势
本机 02:36BL x=6000.5451（比 700 档的 0.4340 还远）应为 ≈0.37
另一台 10:00BL y=600.7918（比 30 档的 0.7662 还低）应为 ≈0.745

旧实现（0.9.38）只剪表尾（while 只比较最后两档），内点原封不动进表。 units_for 把表按 f 排序做分段插值，于是一段区间被彻底带歪：本机那张表 tx≈0.55 的点击被算成 636 单位、实际落在 0.39，偏 246 px。

为什么验证没抓到：validate() 每角只抽 4 个随机点（共 16 个），没抽到那一段； 中位 15.3 px 完全掩盖了一个 246 px 的洞。中位误差不是表的合格证明。

修法（2026-10-25）：clean_table(points, sign) —— 内点判单调性（某点和前后两档 都不同向就删该点），表尾沿用老规则。只判单调、不判斜率大小，是因为指针加速曲线本来 就不均匀（慢速档每单位位移更大），拿斜率卡会把正常档位当离群点删掉（试过，测试立刻挂了）。 修完本机 BL x 12 → 11 档，同一批目标的最大误差 246 → 23.8 px。

复现性结论（两台 Mac，同一台 iPad）：

角位移一致性说明
BR x / BR y4–20 px ✅两次运行互相复现
BL x / BL y272 / 54 px ❌各自的坏点造成的，clean_table 后一致
TL x / TL y72–101 px ❌低速档（150 单位）位移 47 vs 120 px，2.5 倍差
TR x / TR y67 / 39 px同上，越靠近顶角越明显

顶角低速档不可复现，是 iOS 指针加速的历史依赖（上一段移动的快慢影响这一步的增益）， 不是代码 bug——所以「换台机器再校一次」不能保证得到同样的表，这也是必须"当场测"的另一条理由。

2.10 真值 ≠ 终值：光标还在飞的时候读到的 PT 是中途位置（2026-10-25 实测）

现象：两台 Mac 各跑一次 iPad 校准，都没有发送失败、没有 AirPlay 帧告警，却各自产出一个坏点。

排除过的原因：

  • 「不同 Mac 的 AirPlay 延迟不同」→ 不成立。两台实测 188 / 182 ms，而 _settle() = max(0.55 + s/1000*0.25, 延迟+0.08)，188+80=268 ms ≪ 550 ms， 延迟补偿根本没启用，两台机器每一步实际等待时间完全一样。既然等待相同，结果就不可能 因延迟而分叉。
  • 「409 重发导致多走」→ 不成立：两台校准窗口内 409 计数都是 0。

真正原因：一次 move 不是"一下子到位"，而是分多条 HID 报告走完，光标要飞 300–500 ms。校准只等 0.59 s，余量 100–200 ms。把"取帧"(12 ms)和 OCR 拆开、 在精确时刻抓帧后离线识别，4 次试验里 2 次在 450 ms 读到中途位置：

move +150  起点 132.2   284ms:132.2   450ms:170.0   550ms:238.5   ← 450ms 是中途值
move +150  起点 132.2   228ms:132.2   300ms:134.6   450ms:187.6   550ms:238.5

这正好产出两类坏点：读到中途 → 位移偏小（另一台 BL y=60「几乎没动」）； 停车动作还在飞就开始测 → 两段位移叠加、偏大（本机 BL x=600「多走 173 px」）。

关键认识：探针给的是真值，但真值也分终值和中途值——系统当时确实在那儿。 所以 §2.8 说的"有真值就用真值"要补一句：真值也要问对时机。探针解决的是 "帧差算错质心"，解决不了"你问得太早"。

修法（2026-10-25）：探针 HUD 本来就有 AGE（距上次 hover 事件的毫秒数）， probe.py 一直没解析它。现在 parse_age() 读出来，Calibrator.settle_pointer() 发现 AGE < 150 ms 就再等 180 ms 重读，最多 3 轮：

  • 停稳了就不多花时间（本机实测 0.59 s 时 AGE 已经 250–350 ms → 不触发）；
  • 还在飞就等到停；读不到 AGE（老探针）按"已停稳"处理，保持旧行为。

3. 坐标与点击

  • 布局会漂移：信息 App 新建按钮实测 y 0.885 → 0.935；每次按最新截图取坐标。
  • changed=true 不代表成功：hover 只有约 90 px；真实界面变化通常 > 1000 px。用 min_change_px（click_text 默认 500）。
  • 顶部 6% 是 Device.changed() 的盲区（避状态栏时钟）：TL/TR 停车点在 y≈3%，校准里不能用它判变化，要用 _diff_pixels。
  • 边缘够不到：BR/TL 停车点离边约 3–10%，x>0.96 的按钮可能点不到；必要时换角或截图确认。
  • 底部 6% 精度下降（y>0.94）：点控件上沿，或用键盘。
  • 圆角不可达带：iOS 把指针中心夹在圆角内，x<0.15 且 y>0.97 一带物理点不到；重试无意义。 现在有几何模型：control/corners.py + 实测档案 control/corner_profiles.json （源:宽x高 → inset / 半径 R），click 会返回 predicted 落点供对照； 换手机/分辨率先用 python control/measure_corners.py --device "…" 量一份。见 §6.2。
  • 点击默认 aim=True：会先找指针纠偏，多花 1–2 s；返回里的 pointer_err 可判断这次准不准。 pointer_err 突然从个位数变成 ~110 px 说明校准表已经不对（2026-10-22 遇到过一次），别硬补偏移，重校。
  • 右键（click 2，固件 0.6.1+）是应用相关的：备忘录列表能弹菜单，部分第三方列表不响应。 换原生文本/列表界面验证，别拿单个 App 判断固件好坏。
  • MCP 已暴露右键（2026-10-23 实测）：click(x, y, button="right") → 固件 click 2。 实测 N16R8 + iPhone 备忘录列表弹出「共享 / 移动 / 删除 / 置顶 / 锁定 / 复制」（changed_px=14753）。 注意：工具 schema 要宿主重启 MCP 进程才会出现 button（control/mcp_server.py 0.3.1）。
  • 关闭上下文菜单别点看起来“空白”的地方：iOS 的菜单项是整格命中，不是点文字才生效。 2026-10-23 复核：右键备忘录列表第一条 → 菜单顶部一行三格「共享 / 移动 / 删除」（删除在右上格）， OCR 中心 删除=(0.834, 0.406)，面板右缘到 x≈0.95；当年误点的 (0.88, 0.42) 虽然看起来像面板右上的空白，却正好落在删除格里（该格约 x 0.73–0.95, y 0.36–0.47）， 所以当场删掉一条备忘录是真的（已按 §5 的“文件夹移动法”恢复）。 关闭菜单用 esc（本轮实测可关）或点远离面板的空白（如最下方 y>0.85）； 不要点面板内部/边缘的任何“空白”。
  • aim 会误判，别迷信 pointer_err≈0：底部区域实测实际落点比目标低约 30 px， 但 pointer_err 只有 1.0 px——它把界面里的灰色圆/阴影当成了指针。 y>0.9、小图标、或同一目标连续 changed=false 时，把目标上移 0.02–0.03 再点，并重新截图核对。
  • 滚轮其实能用（2026-10-22 实测，iPhone iOS 18 / 内嵌网页文章）：scroll N 0 会让页面动， 但每份报告只走约 4–8 px（图像对齐实测：5 次 ≈ 42 px），且 N 的大小被忽略 （-1 / -5 / -20 位移一样），连发才累加。好处是没有惯性，发完停 0.25 s 就能截图。 所以：整屏翻页仍用分段拖拽（dy）；微调走 scroll(fine=N)。旧文档「iOS 不认滚轮」是错的。
  • 滚轮方向与 dy 相反（已修）：固件 scroll +N 实际是「页面向下」——设置列表和内嵌网页列表 都验证过（2026-10-22 复测）。工具层已把 scroll(fine=…) 取反，与 dy 统一为「正数 = 更早/向上」。 个别表面（视频、部分 WebView）若方向相反，用 设置 → 交互 → 滚轮方向 翻转，别改代码。
  • 滚轮跟着指针走：iOS 只滚「指针下方」的滚动视图。指针停在底部工具栏/空白处时，滚轮一份报告都不生效 （实测 moved_px=0）；scroll(fine=...) 会先把指针停到屏幕中央再滚。自己发 scroll 命令时别忘了这步。
  • 拖拽/滚动松手前必须停住：抬手那一刻 iOS 会按最近的速度结算惯性，边走边松会被当成甩动， 页面再滑一段，截图和坐标就全偏了。drag/scroll 现在松手前停 SETTLE_PAUSE（1.30 s）， 并且 drag 先快后慢（ease-out）、末尾三小步减速（0.55 s 实测仍会被判成甩动）， 松手后先放 0.8 s，再按像素差连续 2 次无位移才截图（_settle_shot，最多约 3 s）。 别用字节比对——同一画面重编码后 JPEG 字节也不同，会一直等不到「相等」；自己写脚本时别省这两步。

4. 校准

  • 校准前先测投屏延迟（实测中位 223–355 ms），等待时间不短于「延迟 + 80 ms」。
  • 网格测试页（静态、高对比、无 hover）是最好的校准画布。
  • 校准表只有一个权威文件：~/Library/Application Support/HIDBridge/calib.json； GUI、MCP、CLI 都读它（HIDBRIDGE_CALIB 可覆盖），仓库里的只是种子。
  • 动作前会自动按 mtime reload；calibration_status.stale=true 说明文件比内存新，调 calibration_reload。
  • 校准完成后不需要重启 MCP（会自动 reload），但用 calibration_status 确认 measured_at 已变。 实测（2026-10-22）：向导写完文件后 MCP 里仍是旧表（stale=true、measured_at 还是上一次）， 调一次 calibration_reload 才生效；这次校准 latency 206 ms、点击 pointer_err 6–33 px。
  • status.calibrated 以控制层 calib.json 的 corners 为准；legacy 的 server_calibrated 另算。

App 请求相机不弹窗、直接拒绝hardened runtime 的 App 缺 com.apple.security.device.camera 权限，TCC 的规则是「缺少权限就不弹窗」entitlements.plist 加 camera；Info.plist 加 NSCameraUsageDescription，两者缺一不可

5. 数据安全（真实踩过）

  • 误删备忘录：文件夹 → 最近删除 → 编辑 → 选中 → 文件夹图标 → 备忘录 可恢复（30 天内）。 iOS 17 的“最近删除”没有单独的「恢复」按钮（只有 移动/删除），别去找；实测 2026-10-23 这条路径有效（abc123 27 → 26 → 27，最近删除 2 → 1）。
  • 不要凭截图判断文本被改：长行会软换行，看起来像被回车拆开；让用户确认或选中复制比对。
  • 修改用户数据（笔记、联系人、设置）前先得到明确同意；测试内容写在自己的测试笔记里。
  • 不要长按敏感页面（备忘录/密码/邮件）：iOS 的预览卡片会明文展开正文，截图会进模型上下文。

9. 便宜板（ESP32-S3-N16R8）：XMC Flash 的坑（2026-10-22 实测）

背景：XIAO ESP32S3 Plus 较贵，改用 YD ESP32-S3-COREBOARD V1.4（N16R8，¥20 级）做实验。 固件改用统一的 s3_16m_universal（见 firmware/hid_bridge/src/board.h）。

9.1 烧官方 16M 镜像后无限重启

  • 现象：串口每 ~0.3 s 刷一次 E bootloader_flash: XMC flash startup fail / failed when running XMC startup flow, reboot!，BLE 名不广播，App 看不到板子。
  • 根因：IDF 5.4+ 的 bootloader_flash_xmc_startup() 用白名单判 XMC（MFID 0x40/0x41/0x50）； 这颗 XM25QH128A 是 MFID 0x70 / CPID 0x18，不在名单里 → 被强制跑一轮复位序列 → 跑完仍认不出 → 重启。原厂固件（老 IDF，无此逻辑）能启动，可用来排除硬件问题。 Espressif 官方表态不修（esp-idf#18947）。
  • 规避：firmware/tools/patch_xmc_bootloader.py（build.sh 的 16M profile 自动调用） 把该函数改成"立即返回 OK"（等价老 IDF 行为），并按 esptool 规则重算 checksum + SHA256。 对非 XMC/白名单内的芯片是恒等变换。
  • 判断命令：esptool flash-id 看到 Manufacturer: 20 / Device: 7018 即可确认。

9.2 用 App 刷机会报串口噪声

  • 现象：Invalid head of packet (0x81/0x30): Possible serial noise。
  • 根因：这块板的 CH343 链路在 460800/921600 下不稳。
  • 规避：刷机用 230400（app/core/firmware.py 已改默认值；115200 也稳）。

9.3 NVS 配置写不进去（已解决，2026-10-23）

  • 现象：串口 cfg<...> 回 ok saved、cfg? 当场能读回，但重启后配置丢失， Wi-Fi 不会自动连。表现为"配了网，一断电就没了"。
  • 根因：Flash 模式不匹配。Arduino-ESP32 核心默认按 QIO 编译；这颗 XMC 的 状态寄存器写不进去（启动日志 Failed to set QIE bit, not enabling QIO mode）， bootloader 把 MMU 回退到 DIO，但运行期 esp_flash_read 仍按 QIO 发读命令 → 读数据分区一律返回 0xFF。写是好的，所以"写成功、读不到"——NVS 的 CRC 校验失败， 键等于不存在。
  • 判定方法：在固件里 esp_partition_write 64 字节后立刻 esp_partition_read， 比较是否一致（match=0 + back=ffffffffffffffff 即是本问题）； 同一地址用 esptool 读却是对的 → 证明"写没问题，固件读路径坏了"。
  • 规避：16M 通用镜像显式用 FlashMode=dio 编译（firmware/build.sh 已固定）。 注意：只给 esptool 加 --flash-mode dio 改镜像头不够，必须重编译 bootloader。
  • 验证：flashprobe → match=1；probe → 同句柄/重开句柄都能读回； cfg 写 → 重启 → cfg? 仍在。
  • 顺带修掉：ConfigStore::save() 原先不检查 put* 返回值，写失败也回 ok saved （App 会显示"已保存"）。现在写后回读校验，失败返回 err nvs write used=.. free=..。
